Context

apps.apple.com is Apple's storefront for iOS, iPadOS, macOS, tvOS, watchOS, and visionOS software: one page per app, one purchase/install flow, one review system. Apple monetizes it through commission on digital-goods transactions — 30% standard, 15% for the Small Business Program, with lower tiers now carved out by regulation (EU Digital Markets Act, Japan's Mobile Software Competition Act) — rather than through a separately disclosed revenue line; App Store income is folded into Apple's undifferentiated Services segment. For an index builder, the interesting object is the numeric trackId (Apple calls it adamId in older docs) printed in every /app/.../id{trackId} URL, plus the bundleId that survives app renames. The defining constraint discovered while probing this site is not a bot wall like Amazon's but a storefront gate: inferred the HTML site negotiates content by requester IP rather than URL path. Basis: requests for explicit /us/ URLs 302-redirected to /cn, and the legacy itunes.apple.com host's 301 hop carried a user-country: CN response header and vary: X-Apple-Store-Front, Cookie (Probe Log). The JSON APIs behind the same catalog are not gated this way.

Retrieval Notes (site-specific deltas)

Only where apps.apple.com differs from the default platform assumptions.

Identifier & dedup

trackId (the numeric ID in every /app/.../id{trackId} URL) is stable and constant across all storefront/locale variants of one app, per the sitemap's hreflang alternates (Probe Log). bundleId is the developer-chosen identifier that survives renames and relistings; URL slugs and the country segment are not stable and should not be treated as identity.

Retrieval unit

The app shell (name, developer, genre) barely changes; the version sub-record (release notes, size, minimum OS, current rating) refreshes on every submitted update — functionally the same two-speed split as Amazon's product-vs-offer, just triggered by app releases instead of price changes.

Cross-modal joins

trackId joins metadata, images, and reviews. artistId/sellerName joins one developer's full catalog. bundleId is the join key into developer-side systems (crash analytics, App Store Connect) that Site Wise cannot reach.

Authoritative content field

Developer-submitted description and subtitle are unmoderated ASO copy. Apple's own genre classification, content rating, and the numeric star rating are closer to ground truth — though rating itself is an adversarial surface, consistent with the 193,035 accounts Apple terminated in 2025 (Verified Metrics).

Freshness & recrawl

Reviews need continuous polling, not periodic recrawl: the customer-reviews feed only ever exposes the 500 most-recent per app per storefront (Probe Log), so a slow recrawl cadence permanently loses review history rather than just serving it stale.

Internal vs external search

inferred Any generic crawler is plausibly subject to the same storefront gate this probe hit. Basis: the 302→/cn fired on an explicit /us/ URL regardless of path, and the response named its negotiation axis directly (vary: X-Apple-Store-Front, Cookie) rather than keying off the URL (Probe Log) — whether Apple allowlists search-engine user agents around this gate is unconfirmed (Open Questions).

User query profile

Install-intent queries (app name, category + qualifier like "photo editor free"), competitive comparisons, and trust queries ("is [app] safe") given the fraud and rejection volumes in Verified Metrics.

Indexing Plan

  • Retrieval unit: app record keyed by trackId, with a version sub-record (size/notes/min-OS) and a review sub-record attached.
  • Primary keys & joins: trackId primary; bundleId secondary/cross-store; storefront country is a dimension on the same trackId, not a separate identity (sitemap hreflang evidence).
  • Ingestion paths, ranked: 1) Lookup/Search JSON API — free, ~20 calls/min, best for refreshing known IDs, weak for discovery. 2) Sitemap crawl of the six index families — the only free ID-discovery path, but the probe sample suggests it surfaces a minority of the official catalog (Risks), so pair with (3). 3) rss.applemarketingtools.com chart feeds — free, no auth, strong for trending/new-app discovery, capped to top-N per chart/country. 4) Enterprise Partner Feed — full weekly + daily-incremental bulk dump including applications, gated behind Performance Partner Program membership and licensed for link-generation only (Risks). 5) Customer-reviews RSS — free per-app review text, hard-capped at 500 most-recent per storefront.
  • Recrawl cadence: version metadata on a chart-driven schedule (daily for top-chart apps, weekly/monthly long tail); reviews via tight continuous polling to stay ahead of the 500-item eviction window; sitemap-based ID discovery weekly to catch new listings and delistings.
  • Derivatives to generate: sentiment/topic extraction over review text (a text corpus Amazon does not expose at all); ASO-keyword-vs-actual-content divergence score from title/subtitle vs. description.
  • Demo to build: a review-window watchdog — poll the customer-reviews feed for a seed set of app IDs on varying intervals and measure how many reviews would be silently lost between polls once arrival rate exceeds the 500-item/page=10 ceiling.

Risks to the Index

  • Geo-gating is server-side and silent: the Probe Log shows a storefront swap triggered by requester IP on an explicit /us/ URL, with no error code distinguishing it from a normal 302 — a crawl fleet's own egress geography determines which storefront it can see, undetected unless checked.
  • Sitemap coverage is a floor, not the catalog: the sampled app-sitemap child implies roughly a quarter of the officially reported app count is reachable by ID-discovery crawl alone; discovery must lean on chart/RSS feeds too.
  • Bulk feed license is narrower than its data: the Enterprise Partner Feed's Performance Partner Program terms restrict use to generating links into Apple Services — a general-purpose index cannot cite EPF as its legal basis for redistributing that metadata.
  • Review history has a hard eviction window: the only free review-text path exposes at most 500 most-recent reviews per app per storefront with no backfill API; missed polling cycles are permanent data loss, not staleness.
  • inferred Regulatory commission carve-outs (EU DMA, Japan MSCA) signal the catalog's monetization terms are jurisdiction-dependent going forward. Basis: three different commission structures now apply to the same catalog depending on storefront (Verified Metrics), so a "price" or "commission" field cannot be treated as a single global constant per app.
