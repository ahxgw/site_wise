Context

Calculator.net is a free collection of single-purpose calculators: mortgage, BMI, age, GPA, concrete and so on. Each sits on one static-looking .html page with a form, and below it a long explainer. It launched on calculators.info in 2007 and moved to calculator.net in 2008. It is run by Maple Tech. International LLC, a small Houston-area company founded by Huiming Gu that also runs unitconverters.net, math.net and usbanklocations.com. Revenue is display advertising (Google AdSense / Ad Manager plus header-bidding SSPs in ads.txt). Most traffic arrives from search. For an index builder this site is the opposite of a platform: the document corpus is tiny and fully enumerable in minutes. The value lies in the function each page exposes. Its form submits by GET, the result is rendered server-side into the HTML, and so every set of inputs is a shareable, crawlable URL. The right index is a tool index: an input schema, an output and a formula per calculator, with a parameterized deep link as the answer.

Retrieval Notes (site-specific deltas)

Only where calculator.net differs from the default platform assumptions.

No two-track split: everything is open

Most profiled platforms keep an SEO sliver for approved crawlers and gate the rest. Here there is no gate at all: an empty * group, no AI-crawler lines, the same bytes for every UA, no WAF, and no login wall on any tool. The constraints are legal rather than technical. The terms forbid commercial copying of "any aspect" of the site, so an index can link and summarize but should not re-host the tools or their text.

The object is a function, not a document

A search user who types "monthly payment on 500K at 6.5%" wants the answer, not the explainer. Every tool is a GET form whose result is rendered server-side, so the answer is one URL away: fill the form fields (chouseprice, cinterestrate, … plus x=Calculate) and link to that URL. The retrieval unit is therefore tool + typed input schema. Field names, units, defaults and <select> options are all in the bare page's HTML, so the schema can be extracted from a single fetch.

Canonicalization is conditional

Result URLs and ?printit=1 point a canonical tag at the bare path. Bare pages, unknown parameters (?utm=) and case variants (/MORTGAGE-…, the site's own /401K-… link) return 200 with no canonical. inferred The PHP template emits the canonical only when it recognizes a form field in the query. Basis: canonical present on ?printit=1 and ?x=Calculate URLs, absent on ?utm=x (Probe Log). A crawler must lowercase paths and strip queries itself, keying on the sitemap's 222 URLs.

Freshness signals are synthetic

Every lastmod equals the day before the probe, cache-control is max-age=1, and there is no Last-Modified on HTML. inferred The sitemap stamps generation time, not edit time. Basis: all 222 dates are identical and equal yesterday, while the CloudFront CSS dates from 2025-06-28. The only real change detection is a content hash of the explainer text with the form's default values masked out.

Metadata lives in microdata and forms, not JSON-LD

With no JSON-LD and no OG, the default "parse JSON-LD for the title, type and image" pipeline returns nothing. The usable structure is the BreadcrumbList microdata (category), <h1>, meta description and form inputs. There is no WebApplication or SoftwareApplication markup, so an index has to synthesize the "this is a tool" type itself.

Crawl budget is trivial; result crawling is the hazard

The whole canonical site is 222 requests and 5.4MB, which is one minute of polite crawling. Following links from archived or third-party result URLs (Wayback alone has thousands) would point an index at an unbounded, near-duplicate space on a single PHP origin with no CDN for HTML. Seed only from the sitemap and never enqueue ? URLs.

Indexing Plan

  • Retrieval unit: one calculator, made up of its title, category, description, typed input schema (field, label, unit, default, options), output labels from a default-value result render, and explainer passages split by <h2>/<h3>.
  • Primary keys & joins: the lowercased slug (mortgage-calculator); the breadcrumb category; form field names as parameter keys. The cross-site join is by concept (mortgage, BMI) to competing tool sites and to sister unitconverters.net converters, which the site links to.
  • Ingestion paths, ranked:
    1. XML sitemap, 222 URLs → one HTML fetch each. That is the entire corpus.
    2. One default-input result fetch per tool (submit the form with its own defaults) to capture the output labels and the table shape. That is 204 more requests.
    3. PDFs and XLS from outlinks, as attachments, with the PDFs attributed to their government source.
  • Recrawl cadence: weekly sitemap diff by URL set, not by lastmod, to detect new tools. Monthly content-hash refetch of all 222 pages.
  • Derivatives to generate: an input-schema JSON per tool; query → parameter slot-filling templates ("X at Y% for Z years" → mortgage fields); a formula summary from the explainer text (not from decompiled JS, which the terms forbid); a cross-site tool-equivalence table.
  • Demo to build: "answer by deep link": parse a natural-language calculation query, choose the tool by embedding match on title and description, fill its GET parameters, and return the calculator.net result URL. The site's own server computes the answer, so the index stores no results.

Risks to the Index

  • Terms bar re-use, not access: commercial copying and reverse-engineering are both forbidden. Re-implementing the formulas from textbooks is fine, but re-hosting the pages or their text is not. Deep links are explicitly welcome.
  • Unbounded near-duplicates: case-insensitive paths, unknown parameters without a canonical, and an open-ended result space. A naive crawler seeded from links in the wild will flood a small single-origin site and its own index.
  • Dates are meaningless: lastmod is regenerated daily, so freshness ranking on it would treat a 2008 tool as new.
  • YMYL answers: financial and health outputs (tax, mortgage, BMI, pregnancy) carry jurisdiction and year assumptions such as US tax brackets. An index that surfaces the computed number should surface the assumptions with it.
