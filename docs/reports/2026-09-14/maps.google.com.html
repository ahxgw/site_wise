Context

Google Maps is the world's largest structured record of physical places — 250M businesses and locations, 2B+ monthly users, 100M edits a day — and, measured rather than assumed, one of the least crawlable large sites on the web. It monetizes twice: local ads inside Search and Maps, and Google Maps Platform, a metered developer API priced per thousand calls. Neither line depends on third parties holding a copy of the data, and the Terms of Service say so explicitly — no scraping, no caching of names, addresses, or reviews, no building a substitute. inferred Maps treats its place graph as a licensed product rather than a published corpus, and enforces that at render time rather than in robots.txt. Basis: the 263-line robots.txt names no AI crawler and Allow: /maps/place/ is explicit, yet the same place URL returns a 19KB rendered record to Googlebot and a 907KB JavaScript shell to ClaudeBot, GPTBot, Bingbot, and DuckDuckBot (Probe Log).

Retrieval Notes (site-specific deltas)

Identifier & dedup

Three identifier systems coexist and only one is licensed for storage: the crawl surface exposes the Feature ID as a hex pair in the URL path (…/data=!4m2!3m1!1s0x89c25090129c363d:0x40c6a5770d25022b), the API exposes the opaque Place ID (ChIJ…), and the CID is the decimal form of the Feature ID's second half. inferred The Feature ID is the only durable key obtainable without a billing account. Basis: the identical hex pair appears in the place sitemap entries and in every result link on the Googlebot-rendered search pages (Probe Log), while every keyless API call returned 403.

Retrieval unit

The place, not the page. A /maps/search/ URL is a query result, not a document — it is a container for up to 20 place records and has no stable content of its own. Indexing the URL as a document duplicates every place across the categories and localities that surface it.

Cross-modal joins

Feature ID joins the crawled name/address/phone triple to the API's full record. Coordinates join positionally through the staticmap markers= list, but only for the first 10 of up to 20 results — the remainder have no geodata on the crawl track. Photos and reviews join by Place ID only, so they are unreachable without a key.

Authoritative content field

The editorial summary ("Classic & seasonal fare served in a warm bistro…") is Google-authored, not merchant-authored, and is the only descriptive text on the crawl track — an abstraction, not ground truth. The crawl track carries no rating or review-count field, so no trust signal travels with it.

Freshness & recrawl

The sitemap's lastmod is a batch stamp, not a per-place signal: 99.8% of URLs share one date (2026-09-04). It tells you when the query list was regenerated, not when any business changed. Against 100M map edits a day, crawled records go stale invisibly.

Internal vs external search

The 29 sitemap categories (restaurants, hotels, pharmacies, mosques, parking, spas…) are Google's own declaration of which local intents it wants external search engines to see. Notably absent: doctors, lawyers, schools, and any category where the listing carries regulatory or safety weight.

Two-track gating

The methodology's default two-track assumption holds here in its sharpest observed form: the SEO sliver and the JS shell are served from the same URL with the same robots.txt permission, discriminated purely by User-Agent string. Nothing in robots.txt discloses the split.

Indexing Plan

  • Retrieval unit: the place record, keyed by Feature ID, with the source query URL kept as provenance rather than as a document.
  • Primary keys & joins: Feature ID (crawl-obtainable) → Place ID (API-only, indefinitely storable) → lat/lng (30-day cache limit). Everything richer joins through Place ID and therefore through a billing account.
  • Ingestion paths, ranked: 1) Places API with a key — full fields, $5–$32/1K, but the ToS forbids retaining names, addresses, and reviews, so it feeds a live lookup, not a corpus. 2) Googlebot-UA fetch of the 87,414 sitemap URLs — free and robots-permitted, ceiling 0.70% of places, name/address/phone/summary only, and it depends on impersonating a UA that Google gates on. 3) No bulk path exists; Street View, tiles, reviews, and photos have none at any price.
  • Recrawl cadence: follow the sitemap's own batch stamp — the search leaves were regenerated 2026-09-04 and 2026-06-12, so monthly is the fastest cadence the publisher's signal supports. Place sitemaps (95 landmarks) are effectively static; quarterly.
  • Derivatives to generate: geocode backfill from the markers= list; entity resolution from the name+address+phone triple against an openly licensed base such as OpenStreetMap or Overture, which is where a retainable corpus has to live. Embeddings do not launder the problem — the ToS prohibits the retention, not the vectorization.
  • Demo to build: a UA-differential crawler that fetches one place URL under seven User-Agents and diffs the rendered payloads, turning the 19KB-vs-907KB gap into a reproducible measurement rather than an anecdote.

Risks to the Index

  • The crawl track is a courtesy, not a contract. Googlebot-only rendering is a server-side UA decision that can change without a robots.txt edit; nothing in the published crawl policy announces it. A pipeline built on it goes to zero silently, so monitor payload size per fetch, not HTTP status.
  • Retention is prohibited, not merely metered. Paying for the API does not buy a corpus: ToS §3.2.3(a)(iii) names business names, addresses, and user reviews specifically, and §14.3 permits caching only lat/lng for 30 days. A Maps-derived place index cannot legally persist, so Maps has to be a live enrichment call, not a shard.
  • Substitute clause blocks the obvious product. The ToS bars using the Core Services in a listings or directory service, or to create a substitute of Google Maps — which is precisely what a full-modal place index looks like from the outside.
  • Price steps are volume-cliffed. Place Details Essentials runs $5.00/1K up to 100K calls and $0.38/1K above 5M — a 13× unit-cost spread, so batching strategy is a procurement decision, not an engineering one.
  • Single-vendor imagery dependency. Street View and satellite layers have no bulk path at any price tier and no alternative supplier at comparable coverage, leaving imagery-dependent features un-hedged.

Inferences

  • Maps enforces access control at render time rather than in robots.txt. Basis: the 263-line robots.txt contains zero AI-crawler directives and explicitly allows /maps/place/, yet the UA matrix probe shows the same URL returning 19,136 bytes of rendered record to Googlebot and 907,279 bytes of empty JS shell to ClaudeBot, GPTBot, Bingbot and DuckDuckBot.
  • The Feature ID is the only durable place key obtainable without a billing account. Basis: the hex pair 0x…:0x… appears in both the place sitemap entries and every result link on Googlebot-rendered search pages, while all six keyless API probes returned 401/403.
  • Google's sitemap categories are a deliberate disclosure choice, not a coverage artifact. Basis: the 29 categories include mosques, synagogues, temples, spas and parking at ~4–5K URLs each, while 11 others collapse to a single "near me" URL, and no regulated-professional category appears at all.
  • The crawl track cannot support trust scoring. Basis: zero occurrences of "rating", "review", "hours" or "open" across the 22,794-byte Googlebot search page and the 19,136-byte place page, and the place page's only JSON-LD node is @type: WebPage.
  • Crawled records go stale without any signal. Basis: 87,204 of 87,414 sitemap URLs share the single lastmod 2026-09-04, against an official 100M edits/day.
