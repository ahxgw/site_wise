Context

NHL.com is the National Hockey League's official site. It hosts league news, video highlights, scores and stats, and since the 2023/24 relaunch on Deltatre's FORGE publishing platform it also serves a site for each of the 32 clubs, under paths like /bruins/ (Deltatre case study). The site makes money from ads, the shop, tickets and app subscriptions. The league's main revenue is media rights, for example the C$11B Rogers deal that started with the 2026-27 season. For an index builder, nhl.com is unusual among top sites. Its HTML is thin and carries no JSON-LD, but the two backends the front end reads from are open without a key and paginate without a cap. One is a content API covering stories and videos in 8 languages. The other is a stats API that goes back to the 1917-18 season. Both share the same player and team IDs, so text, video and structured game data join cleanly. The terms of service still prohibit "unauthorized" scraping, so the open APIs are a technical path, not a licence.

Retrieval Notes (site-specific deltas)

Only where nhl.com differs from the default assumptions.

The API is the corpus; the sitemap is a 24-hour window

The two content sitemaps each hold only the newest 100 items, and the static sitemap has no articles at all. A sitemap-driven crawler would see under 0.1% of the 650K stories and videos (calculated by Site Wise). forge-dapi has no depth cap, so the whole archive can be read in about 6.5K pages of 100 (calculated by Site Wise). That makes this the rare top site where a full metadata census costs hours, not a crawl.

Two robots policies, split by host

www.nhl.com names no AI crawlers. The nhle.com data hosts carry Cloudflare's managed file, which says ai-train=no, search=yes and blocks 30 AI and secondary bots by name. This is the reverse of the usual pattern: the HTML is open and the structured backends are fenced. A search-only index fits the search=yes,use=reference signal. Record the signal per object and keep it out of any training export.

Player ID is a cross-modal join key

The playerid-{n} tags, the forge-entity slugs (name-{n}) inside story markdown, and the stats playerId are the same integer. teamid-{n} matches the stats team id. That joins articles, video clips, box scores and shot coordinates without NER. The game ID is the remaining gap: stories don't expose it as a tag in the sample, so tie highlights to games by date, team and player.

Identifiers and translations

The API slug equals the URL slug. League stories live at /news/{slug}, club stories at /{club}/news/{slug}, and video slugs end in the brightcoveId. Each locale item has its own _translationId and _entityId. Whether a French or German item shares an _entityId with an English original is open. The sampled non-English headlines were original local pieces, not translations, so treat each edition as its own corpus.

Archive dates are editorial, not crawl-time

The deepest items carry contentDate values from 1959–60 and 1994, decades before the site existed. These are backdated historical pieces and migrated archives. Use contentDate for "when it happened", lastUpdatedDate for recrawl, and never infer a site-launch date from item dates.

Play-by-play fidelity is era-dependent

The same endpoint returns 15 plays for a 1990 game and 361, 81% with rink coordinates, for 2025 (Probe Log; share calculated by Site Wise). Index the event table with an era-quality flag, so shot-location queries don't silently return only post-2010 results as if they covered all eras.

Indexing Plan

  • Retrieval units: the story (with its markdown parts as passages), the video clip (title, long description, duration, thumbnail, later its transcript), the game (with its play events) and the player season. Entity pages are synthesized as player → {stories, clips, games, stats}.
  • Primary keys & joins: _translationId per item, with the slug and locale as URL keys. brightcoveId for video. playerId and team id as shared entity keys. Game ID {season}{type}{nnnn} for events.
  • Ingestion paths, ranked: 1) A forge-dapi list walk per locale and type: about 6.5K requests for the English stories and videos at 1 req/s, roughly 1.8h (calculated by Site Wise). Then detail fetches for parts, about 275K requests, so walk newest first and stop at an era cut-off. 2) The stats /game list in one call, then play-by-play per game for coordinate-era seasons. 3) The Google News and video sitemaps every 15 minutes, as the change feed. 4) The static sitemap monthly, for club pages.
  • Recrawl cadence: live games every 15s while in progress. New stories and videos from the sitemaps every 15 minutes. Detail records re-fetched when lastUpdatedDate moves (sample with a daily list delta over the newest 1K). Historical games are frozen once gameState is OFF.
  • Derivatives: ASR on clips: at 230/day of short highlights (sampled clip 1:41) this is cheap, if a licensed playback path exists. Entity linking is free from forge-entity markup. Shot-map images rendered from coordinates. Embeddings on headline, summary and markdown.
  • Demo to build: "player timeline". Given a player ID, merge their stories, video clips and per-game events into a single chronology, so you can check whether the forge tags and the stats IDs really join without fuzzy matching.

Risks to the Index

  • The open APIs are undocumented and unlicensed. The ToS ban "unauthorized" automated harvesting and grant no data licence (Probe Log). Build to tolerate a key requirement appearing overnight, keep request rates browser-like, and keep a sitemap-only fallback.
  • The vendor stack can change. FORGE (Deltatre), Brightcove and Cloudinary all sit under a single league contract. Pre-FORGE story URLs carried numeric suffixes; the 2016 relaunch announcement itself lives at …-278049644 (NHL.com, 2016), while current slugs have none. Store old URLs as aliases and key on brightcoveId and playerId, which outlive CMS swaps.
  • inferred Cloudflare may extend its AI-bot policy from the API hosts to www. Basis: both host families are already on Cloudflare (server header, __cf_bm), and only the nhle.com hosts serve the managed Content-Signal robots file today. A one-toggle change would bring the HTML under the same 30-bot block, so watch www robots.txt for drift.

Open Questions

  • Brightcove renditions, caption tracks and geo restrictions per clip. Closeable with one Playback API call through the public player for a sampled brightcoveId, counting sources, text_tracks and geo.
  • Whether non-English items share _entityId with English originals. Closeable by fetching 50 fr-ca and de-de details and matching _entityId against en-us lookups.
  • Total photo and image count (/v2/content/en-us/photos) and per-club story split. Closeable with the same $skip binary search, and with context.slug=teamid-N filters.
  • Whether a documented, licensed data feed exists for third parties, and its terms. Closeable by asking NHL digital or partnerships, and checking the league's official data-distribution partner terms.
  • Whether the /devils/info/game-day/ sitemap block (2,973 URLs) is a deliberate SEO experiment or a stray export. Closeable by diffing sitemap.xml weekly and checking whether other clubs' equivalent paths return 200.
