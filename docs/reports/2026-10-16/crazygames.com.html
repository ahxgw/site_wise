Context

CrazyGames is a free, ad-funded portal for games that run in the browser. Third-party studios publish to it through a self-service developer portal, launched in October 2018, and are paid a share of ad revenue (plus in-game purchases for selected titles). New games go through a 7–21 day "Basic Launch" test with monetization off. The best performers get a "Full Launch" with the CrazyGames SDK. The company was founded in 2014 in Leuven, Belgium, by Raf and Tomas Mertens. Smartfin invested more than €10M in a growth round. For an index builder, the site is a catalog of playable applications: each game is one well-structured record (title, developer, genre, tags, rating counts, engine, publish date, cover art, a preview clip and controls). The playable build sits on a separate noindex host. The text is thin marketing copy, so the useful modalities are the structured record, the cover and video assets, and the game itself, which only a headless browser can "read".

Retrieval Notes (site-specific deltas)

Only where crazygames.com differs from the default platform assumptions.

Open crawl, crawler-specific enrichment

Unlike the default two-track split, nothing is gated: robots.txt blocks no AI crawler, and every UA gets the same game record. The difference is additive. Only a Googlebot UA gets the 64-game related list rendered server-side, so other crawlers see about a third of the internal game links. inferred The check is a UA string match, not IP verification. Basis: a spoofed Googlebot UA from a non-Google IP got isCrawler:true, while Bingbot got false (Probe Log). For an index this matters only for link-graph features. The sitemap already gives full coverage.

The SSR record beats the JSON-LD

JSON-LD gives name, description, rating, author and date. The __NEXT_DATA__.game object adds the keys that join modalities: a numeric id, developerId, technology, loaderConfig, three cover crops, the video file, allowEmbed, hasIap and the device-friendliness flags. Parse both and keep the SSR record as authoritative. JSON-LD image points at the auto-cover, while og:image points at a different 16×9 crop.

Identifier & dedup

The key is the slug (/game/{slug}); id is the stable internal key. Slugs carry 3-letter disambiguating suffixes (monster-truck-evolution-ojg, global-city-qkk), so a title is not unique. Each locale page is self-canonical with full hreflang, so 25 URLs collapse to one game. Where the description is untranslated, the localized page is a near-exact duplicate: collapse by id and keep only the translated text.

The game itself is the unindexed modality

Titles and 116-word blurbs say little about gameplay. The richest signal is the 169KB trimmed preview clip that every sampled game has, and beyond that the playable build. Keyframes, a CLIP-style embedding of the clip, and OCR of in-game UI make "games like X" and "the one where you drift a police bike" answerable. The builds are versioned and noindex, so they should be rendered for features, never stored or served.

Freshness has no date signal

No lastmod anywhere, and game pages are max-age=0. addedOn exists per game, and 63% of sampled games are from 2024–2026, so the catalog turns over quickly. New games appear on the /new listing (10 pages). Ratings and votes change daily, while descriptions and covers rarely do.

Quality & spam

Every game is curated: status: PUBLISHED in all 60 sampled games, and all go through QA before Basic Launch. So there is no UGC spam tier. The quality signals are the vote count (153 to 316K) and the rating. Titles show SEO-style clone naming ("fps-commando-gun-shooting-game"), so downweight title-only matches against the record's tags and developer.

Indexing Plan

  • Retrieval unit: one game, made up of its SSR record (IDs, engine, developer, category, tags, rating and votes, addedOn), English description, controls and FAQ, 3 covers, the preview clip with derived keyframes, and translated descriptions where they really differ.
  • Primary keys & joins: id and slug; developerId to the developer's other games; tag and category slugs; desktopUrl and buildId for the build. Cross-site joins go by developer name and title to Poki, Itch.io and app stores. Store URL fields exist but were null in the sample.
  • Ingestion paths, ranked:
    1. English XML sitemap (one 683KB fetch) → 4,495 game pages at 1 req/s, which takes about 75 minutes.
    2. Locale pages only for locales where translation is confirmed, decided by a hash diff of descriptionFirst against English. Up to 108K more fetches, so sample before committing.
    3. Preview MP4 and covers from videos. and imgs.: 2 media fetches per game.
    4. Headless render of /embed/{slug} for screenshots, only where allowEmbed is true and only for features.
  • Recrawl cadence: diff the English sitemap URL set daily for new games. Refetch the top games weekly by vote count for rating and vote drift. Refetch everything else monthly.
  • Derivatives to generate: 5–10 keyframes per preview clip, image and clip embeddings, OCR of on-screen UI text, a canonical genre/mechanic label set mapped from the 555 tags, and a per-game embed-eligibility flag.
  • Demo to build: "find a game by what it looks like": embed the 4,495 preview clips and answer visual and gameplay queries, comparing against tag and description retrieval.

Risks to the Index

  • Developer-owned assets: covers, clips and builds belong to 2,000+ third-party studios, not to CrazyGames. Display rights end at thumbnail and link, and some games set allowEmbed: false (21 of 60).
  • Crawler-conditional markup: if the enrichment check moves from UA to verified IP, or extends to other bots, the link graph seen by an index will change. The game records would not.
  • Heavy, versioned builds: a naive crawler following loaderConfig URLs pulls Unity bundles of up to 250MB per game. Never enqueue files. or games. URLs.
  • Flash via Ruffle: 4 of 60 games are SWF emulated in the browser, and files. robots.txt hides .swf from Googlebot. These builds may disappear or change engine without a URL change.
