Daily Site Profile

bookmyshow.com

BookMyShow is India's dominant ticketing platform: a perishable showtime-and-seat corpus, edge-blocked to every agent except the verified search crawlers its llms.txt courts.

Context

BookMyShow sells tickets for cinema, concerts, comedy, theatre, sports and activities across India, and since 2024 it also produces the biggest of those shows — it promoted Coldplay's 2025 India tour itself. That shift shows up in the accounts: live events grew 66% year-on-year to ₹756 Cr in FY25 and now supply 40% of total income, against 12% growth for the older movie-ticketing line (Verified Metrics; percentages calculated by Site Wise). For an index builder the object here is not a document but an offer against finite inventory: a seat, at a price, at a venue, at a time, that stops existing when it sells or when the show starts. BookMyShow's public posture matches the asset. There is no partner or affiliate API, the eleven sitemaps its own robots.txt advertises return 403, and the entire HTML surface is Cloudflare-blocked to unverified agents. What it does publish for machines is a 54KB llms-full.txt instructing AI agents to parse city-page JSON-LD they cannot fetch.

Retrieval Notes (site-specific deltas)

Only where BookMyShow differs from the default platform assumptions.

Identifier & dedup

ET######## is a single namespace spanning movies, events, plays, sports and activities — the activity page's app deep link resolves ET00089258 under /events/ while the web URL says /activities/, so section is a routing label, not an identity. Person IDs are a sequential legacy space (A. R. Rahman is 38; recent entries pass 2M), which dates the catalog usefully. City slugs need a lookup table, not slugification: Delhi-NCR is national-capital-region-ncr.

Retrieval unit

Two units, not one. The title/event (ET ID) is a durable document. The showtime (venue code × date × time × price class) is an inventory row with a lifespan of hours. Indexing only the first gives a catalog nobody queries; indexing only the second gives an index that is wrong by lunchtime.

Cross-modal joins

Unusually clean: image filenames embed the lowercase ET ID and artist filenames embed the person ID, so media joins to entities by string match with no metadata lookup — worth exploiting given the wall blocks metadata but not the CDN. The join that breaks is entity→person: the JSON-LD url field is wrong (Probe Log) and must be rebuilt as /person/{slug}/{id}.

Authoritative content field

Prefer JSON-LD over OG — OG is duplicated and mistyped (og:type=movie on an activity). But JSON-LD needs a repair pass: non-ISO dates and durations, URL/BreadCrumbList casing, and timestamps that label IST as UTC. Treat doortime plus the venue city as the truth for start time and discard the Z.

Freshness & recrawl

Cadence follows the showtime clock, not an interval: a row is worth refreshing until it starts and worthless after. Onsales invert it further — the Coldplay onsale cleared a stadium against 13M users, so a one-minute-old snapshot is already misleading.

Quality & spam

The manipulation surface is resale, not content. Inventory that sells out in minutes reappears on secondary markets at multiples, so an index showing "sold out" next to third-party listings is feeding a scalping market it cannot verify.

Internal vs external search

Inverted relative to most sites in this series. BookMyShow wants external search on its catalog — hence 11 sitemaps and a hand-written llms.txt — but the field users need (is there a 7pm seat near me tonight) is the one no external index can hold fresh. External search can only route to the site, never substitute for it.

User query profile

Almost every query is implicitly geo- and time-scoped: title + city, "movies near me tonight", venue + date. The llms.txt concedes this, telling agents to append a city to every URL to "avoid geographic hallucinations" — a query without a city is unanswerable here.

Indexing Plan

  • Retrieval unit: the title/event keyed by ET ID, as a durable document, with showtime rows attached as a separate fast-expiring table keyed by (ET ID, venue code, date, time).
  • Primary keys & joins: ET ID everywhere; venue 4-letter code; person ID; city slug via lookup table. Media joins by filename substring (lowercase ET ID / person ID). Rebuild person URLs — never trust the JSON-LD url.
  • Ingestion paths, ranked: 1) Image CDN — open, unmetered, and the only path that works today; take posters, banners and headshots and derive the ET/person key from the filename. 2) llms-full.txt — 308 city-templated URL patterns, effectively a hand-written sitemap that is served; use it to enumerate the URL space even though the URLs themselves 403. 3) Internet Archive CDX + replay — the only historical text and JSON-LD source available without allowlisting; a floor, not coverage. 4) Verified-crawler access — requires being a search engine BookMyShow recognises. 5) Showtimes and seat counts — no legitimate path at any price; treat as permanently out of index.
  • Recrawl cadence: titles/events weekly; person and venue records monthly; images only when the filename mtime changes (free change detection); showtimes not at all, since the path doesn't exist — link out to the live page instead.
  • Derivatives to generate: a JSON-LD repair layer (ISO date/duration normalisation, timezone correction from venue city, property-casing fixes, person-URL reconstruction) applied before ingestion; poster embeddings for title dedup across regional-language releases; a city-slug concordance.
  • Demo to build: a "wall map" — hit every URL class BookMyShow publishes for machines (11 declared sitemaps, llms.txt, llms-full.txt, ads.txt, sample detail pages, CDN assets) and render which return 200 and which 403, next to what the llms.txt instructs an agent to do with each. The gap between the two is the deliverable.

Risks to the Index

  • The published crawl contract is already broken. robots.txt declares 11 sitemaps; all 11 return 403 (Probe Log). A pipeline that trusts robots.txt as an access spec fails on the first request, and fails with a 403 — indistinguishable from a temporary block.
  • inferred The llms.txt is marketing, not an access grant. Basis: it instructs agents to parse JSON-LD on city pages that return 403 to every client tested, including a Googlebot-UA request (Probe Log).
  • inferred The AI-crawler stance is unstated, not permissive. Basis: robots.txt names zero AI crawlers, so by the letter of the file they are allowed — but the edge blocks them anyway. Policy lives in Cloudflare's bot rules, which change without touching any file you can monitor.
  • The image CDN is the single point of failure. It is the only unwalled path and sits on a different stack (ImageKit/CloudFront) from the walled origin (Probe Log). One config change closes the last open door.
  • Live inventory leaks through JSON-LD and probably won't keep doing so. Offer.inventoryLevel exposes remaining seat counts for SEO benefit; it is competitively sensitive and cheap to remove.
  • Ownership is in play. Network18 holds 37% and KKR has been reported in talks for a large minority stake (Verified Metrics). A control change is the most likely trigger for a partner-API programme — or for a harder wall.

Inferences

  • The llms.txt is marketing rather than an access grant. Basis: its instructions target pages that return 403 to every client tested, including a Googlebot-UA request (Probe Log).
  • The AI-crawler stance is unstated rather than permissive, and enforcement lives at the edge. Basis: robots.txt contains zero AI-crawler directives while Cloudflare 403s all HTML regardless of UA (Probe Log).
  • The bot allowlist is IP/reverse-DNS verified, not UA-based. Basis: a spoofed Googlebot/2.1 UA received the same 5,488-byte Cloudflare 403 as an honest UA (Probe Log).
  • BookMyShow hosts no video of its own. Basis: the sampled VideoObject.embedUrl is a youtube.com watch URL, and the sibling Clip.potentialAction target is empty (Probe Log).

Open Questions

  • True live corpus size — ET IDs, cinemas, screens, upcoming events. Closeable only by reading the declared sitemap index, which 403s; a verified-crawler fetch or a partner feed would settle it.
  • Whether a reverse-DNS-verified Googlebot actually receives 200. Closeable with a Search Console URL inspection on a BookMyShow-owned property, or a fetch from a Google-owned IP.
  • Size and structure of the user review/rating corpus, and whether it ever appears in structured data. Closeable by sampling movie pages during a release week once page access exists.
  • Whether Offer.inventoryLevel is real-time or a cached snapshot. Closeable by polling one event page through a booking window and comparing the JSON-LD value against the live seat map.
  • Current registered users and monthly ticket volume — no official figure since the company stopped publishing them; needs a BookMyShow disclosure or an investor deck.
  • Whether BookMyShow's non-India properties (Sri Lanka, UAE, Indonesia, West Indies) share the ET ID namespace or run separate ones. Not probed; closeable by sampling a foreign host's detail-page IDs.
