Context

Epic Games is the private company behind Fortnite, Unreal Engine and the Epic Games Store. Tim Sweeney founded it in 1991, and it is based in Cary, North Carolina (Wikipedia). epicgames.com is the umbrella domain: corporate pages and news under www…/site/, account and login, help, and the PC store on store.epicgames.com. Its sister hosts are fortnite.com, unrealengine.com and fab.com. The store sells third-party PC games for a 12% cut and gives away free games weekly. Fortnite increasingly makes money from user-built "islands": Epic pays creators from an engagement pool and says it has paid out more than $1B since 2023. For an index builder, the site splits in two. Every HTML page Site Wise tried, on six Epic hosts, returns a Cloudflare challenge to a non-browser client. The JSON behind them does not. The store's CMS, the free-games feed and the documented Fortnite Data API all answer without a key. The richest open object is the Fortnite island, a playable UGC world with a stable code, a creator handle, tags, a genre rank and daily engagement numbers.

Retrieval Notes (site-specific deltas)

Only where epicgames.com differs from the default platform assumptions.

The gate is the network, not robots.txt

Epic's archived robots.txt is one of the most permissive of any top site: no AI-crawler groups and only account paths blocked. The block sits in front of it. Cloudflare challenges every HTML request, robots.txt included, whatever the UA says. A crawler that treats a 403 on robots.txt as "disallow all" will skip Epic entirely; one that treats it as "allow all" still cannot fetch a page. The practical crawl surface is the JSON hosts the store's own front end calls. They are not challenged, because the SPA needs them.

Island code is the join key

NNNN-NNNN-NNNN is the code players type in-game. It joins the island list, metrics, genre rank and creatorCode, a lowercase handle that is the only creator identifier the API exposes. Store objects key differently: catalog namespace + offer id for commerce, and a URL slug for CMS pages. The slug is the only key shared between the sitemap and the content API.

Authoritative fields

For islands, the title is emoji-laden and keyword-stuffed ("🔄 Reload Solo Scrims | 7777 🏆"), so rank on tags and genre, and use the title only for display. category marks licensed IP and is cleaner than title matching for "Star Wars maps". For products, take developer and publisher from customAttributes or developerAttribution, not from the seller name. The seller is often a distributor, for example "Gameplay Group International" for a Mane6 game.

Most of the island corpus is dormant

Only about 30% of islands record five players on any day of a week, and none of the 25 newest did. A search index that ranks by the API's engagement will naturally bury the long tail. Keep dormant islands in the index but out of the default ranking, and use weekly uniquePlayers as the prior. Generic titles repeat across creators ("1v1" ×182, "BOX PVP" ×169), so deduplicate on code, never on title.

Query profile

Store queries are game titles plus "free" or price. Fortnite queries are map codes, map-type slang (zonewars, boxfight, deathrun, tycoon) and IP names. Treat a 12-digit dashed number as an exact-match key, and map the slang to the API's tag vocabulary.

Indexing Plan

  • Retrieval unit: the Fortnite island (code, title, creator, tags, genre and rank, a 7-day engagement vector) and the store product (slug, About text, developer, publisher, price and promo state, key art). Blog posts are secondary text documents linked to products by slug.
  • Primary keys & joins: island code ↔ creatorCode ↔ genre rank; product slug ↔ catalog namespace/id (promo feed) ↔ blog links. Fortnite itself is both a store product (/p/fortnite) and the host of all islands, the one bridge between the two graphs.
  • Ingestion paths, ranked: 1) The Fortnite Data API: full list in about 12 minutes, metrics per active island only (≈85K calls, calculated by Site Wise from 30% of 283K), no key. 2) The store content API for products and blog, seeded by the archived sitemap (≈1.3K slugs) and extended with slugs found in blog links and promo feeds. Coverage of the 6,000+ catalogue is capped by slug discovery. 3) The promo feed weekly. 4) HTML only through a verified-crawler arrangement, or not at all.
  • Recrawl cadence: island list page 1 hourly (new releases come first); full list weekly to catch deletions; metrics daily for active islands, because the 7-day window means missed days are lost for good; genre ranks hourly if ranking matters. Products weekly and on promo change; blog daily.
  • Derivatives to generate: a persisted daily engagement history per island, which Epic does not keep public beyond 7 days; title normalisation (strip emoji and version numbers) for deduplication; a tag-to-slang synonym map.
  • Demo to build: an "island launch tracker". Poll page 1 hourly, record each new code's first-seen time, and follow its daily unique players for 7 days. That gives a public survival curve for UGC game launches (what share of new islands ever reach 5 players) using only the documented API.

Risks to the Index

  • The open JSON hosts are an unadvertised exception. store-content-ipv4.ak and the promo feed are the store SPA's own backends, not documented APIs. If Epic moves them behind the same Cloudflare rule as store…/graphql and egs-platform-service, the store track closes in one change. Build the index so the Fortnite Data API track, which is documented, stands on its own.
  • Metrics expire after 7 days. Any gap in daily collection is permanent. Run the collector with alerting, not as a best-effort crawl.
  • The HTML wall also blocks archivers. Wayback's March 2026 captures of both robots.txt files are 403s, so historical backfill of corporate and help pages from the archive will have holes.
  • Platform-policy exposure. Epic's store and Fortnite availability depend on its app-store disputes. The regionBlock: "IOS" field on Fortnite's product page shows availability is region- and platform-dependent, so index availability per platform, not as a single flag.

Inferences

  • Search engines reach Epic's HTML through Cloudflare's verified-bot path rather than by UA. Basis: a Googlebot UA from this egress got the same 403 challenge as curl, while robots.txt (archived) allows all crawlers and publishes sitemaps, which would be pointless if no crawler could pass.
  • About 70% of discoverable islands are effectively dormant. Basis: 28 of 40 random islands returned null for every day of 09-20 to 09-25 under the documented 5-player floor. The sample is small, so ±15 points.

Open Questions

  • How many store product slugs exist beyond the 1,280 in the archived sitemap. Could be closed by harvesting slugs from all 3,093 blog posts' links and all locale promo feeds, then deduplicating against the sitemap, or with a live sitemap fetch from an unchallenged network.
  • What the /site/cosmos/ and /site/stardust/ child sitemaps contain. Could be closed by fetching them from a network Cloudflare does not challenge, or by asking the Wayback Machine to save them.
  • Why the en-US blog feed ends at 2026-07-30 (10 posts in July against 28–45 a month in January–May). Could be closed by comparing other locales (/api/{locale}/content/blog) and checking whether store news moved to a different content type.
  • New-island creation rate. The list has no date field. Could be closed by polling page 1 hourly for a week and counting unseen codes (the demo above).
  • The Fortnite Data API rate limit. A 429 is documented but no threshold is published and none was hit at ≤1 request per second. Could be closed with a controlled ramp from a separate IP.
  • Whether the island thumbnail and description are reachable without the challenged fortnite.com HTML. Could be closed by inspecting the in-game discovery service's public endpoints or fortnite.com/@creator/code from an unchallenged network.
