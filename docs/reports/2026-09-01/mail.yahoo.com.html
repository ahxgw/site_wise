Daily Site Profile

mail.yahoo.com

Yahoo Mail moves 25B messages a day behind exactly one public page; the only legitimate index path is per-user OAuth2 IMAP.

Webmail Auth-Walled IMAP / OAuth2 Apollo-Owned Zero-Crawl

Evidence: verified inferred (must state basis) open — conventions in the methodology.

Context

Yahoo Mail launched Oct 8 1997 out of Yahoo's RocketMail (Four11) acquisition and is now run by Yahoo Inc., which Apollo funds bought from Verizon for $5.0B, closing Sep 1 2021. It monetizes a free ad-supported inbox against Mail Plus ($5/mo, ad-free, 200 GB) and standalone storage plans. For an index builder this is the useful inverse of every other top-200 site: the corpus is one of the largest text-and-attachment collections in existence, and essentially none of it is addressable. The public web surface is a single 18.9KB JavaScript shell with no links, no JSON-LD, and no sitemap; every other path 302s to login.yahoo.com (Probe Log). What can be indexed is indexed per mailbox, with the account holder's consent, over standard IMAP, CalDAV and CardDAV — and Yahoo gates those OAuth2 scopes behind a manual partner review rather than a developer console. The engineering question is therefore not "how do we crawl this" but "given a delegated token, what is the retrieval unit and what does the protocol let us sync incrementally".

Retrieval Notes (site-specific deltas)

Only where Yahoo Mail departs from the default platform assumptions.

Identifier & dedup

The default assumption that a canonical URL keys the object fails outright: nothing here has a URL. Yahoo advertises OBJECTID (RFC 8474), so the server issues an EMAILID that survives moves between folders and a MAILBOXID that survives renames — strictly better than the IMAP UID, which is per-folder and dies on a MOVE. Key on EMAILID; keep the sender's Message-ID header as the cross-provider dedup key, since the same thread indexed from a Gmail participant will collide there and nowhere else.

Retrieval unit

Three units, and the message is the wrong default for two of them. Retrieve the message for recall, the thread (THREADID) for presentation, and the attachment as its own document — a 39.8 MiB-capped PDF carries more indexable text than the mail that delivered it, and users search for the file, not the covering note.

Cross-modal joins

Stable: EMAILID → MIME part number → attachment bytes; THREADID → messages. Semi-stable: the participant email address joins messages to CardDAV contacts and CalDAV attendees, but Mail Plus permits 500 aliases per account (Verified Metrics), so one human legitimately fans out across hundreds of addresses. Alias resolution is a first-class entity problem here, not a cleanup step.

Authoritative content field

Reverse of the SEO case. Bulk mail ships a keyword-thin text/plain alternative beside a rich text/html part; personal mail is the opposite. Index both alternatives rather than picking one. The subject line is the least reliable field — it is copied unchanged down long reply chains and stops describing the content by the fourth message.

Freshness & recrawl

The sharpest constraint on this host. Yahoo omits CONDSTORE and QRESYNC (RFC 7162), exposing a proprietary XYMHIGHESTMODSEQ instead, so the standard "give me everything changed since MODSEQ n" resync is unavailable. IDLE covers new arrivals while connected; flag and delete changes that happen while disconnected require re-listing UIDs per folder. Budget for full UID sweeps, not deltas. Deletion has a floor: 12 months of inactivity can remove messages outright on free accounts (Verified Metrics).

Quality & spam

Elsewhere spam is a contaminated minority of the corpus; in a mailbox it is most of the arriving volume and it is already labelled — SPECIAL-USE marks the Junk folder, giving a free, user-corrected training signal. The manipulation to defend against is inbound phishing aimed at the mailbox owner, not ranking abuse aimed at a search result.

Internal vs external search

There is no external option to escape to — site:mail.yahoo.com can only ever return one page. Yahoo's own answer is AI in the client rather than a better query box: one-line generated summaries, a priority inbox, and Quick Actions that lift bills, verification codes, and tracking numbers out of message bodies (announced Nov 14 2024).

User query profile

Known-item retrieval over a small personal corpus: "the flight confirmation", "the invoice from March", sender- and date-bounded lookups. Ranking matters far less than recall and precise filtering, which inverts the usual web-index priority.

Indexing Plan

  • Retrieval unit: message, with the thread as the presentation envelope and each attachment promoted to a sibling document.
  • Primary keys & joins: accountId + EMAILID (RFC 8474) as the primary key — never the folder UID. THREADID groups; the RFC 5322 Message-ID header dedups against the same thread arriving through another provider; normalized participant address joins to CardDAV contacts and CalDAV attendees.
  • Ingestion paths, ranked: 1) IMAP with XOAUTH2 — the only path to message bodies, and it requires the manual partner review at senders.yahooinc.com, not a console signup. 2) CardDAV + CalDAV under the same grant, for the entity layer. 3) SMTP OAUTHBEARER for send-side actions only — it indexes nothing. 4) POP: last resort, no folders and no OBJECTID. 5) Public crawl: one page, permanently.
  • Recrawl cadence: IDLE on Inbox and Sent for arrivals; a per-folder UID sweep nightly to catch flag and delete drift, because CONDSTORE is unavailable (Retrieval Notes); CalDAV/CardDAV REPORT sync weekly; the marketing page quarterly.
  • Derivatives to generate: attachment text extraction and OCR — the highest-value derivative here, since documents carry the densest text and Yahoo exposes no extracted-text field; alias→identity resolution tables; thread summarization; and entity extraction for the order/booking/invoice records that Quick Actions proves are reliably parseable.
  • Demo to build: a consent-scoped IMAP indexer run against a mailbox the operator owns — resolve EMAILID/THREADID via OBJECTID, split attachments into their own documents, and measure the cost the missing CONDSTORE imposes by timing a full UID resync against a simulated delta sync.

Risks to the Index

  • Access is a relationship, not a key. Yahoo states it "no longer support[s] proprietary Mail APIs" and that the mail scopes "are not available for self-served setup in the developer console"; approval runs through a form or mail-api@yahooinc.com and is revocable for misuse (developer access). An index built on it can be switched off by a policy review rather than a rate limit.
  • Quota is undefined. The same page reserves the right to "impose rate limiting if appropriate or necessary" with no published figure, so ingestion throughput cannot be capacity-planned before approval.
  • The corpus is shrinking by design. Free storage moved to 20 GB with over-limit mailboxes blocked from sending and receiving, and inactive accounts face deletion at 12 months (Verified Metrics). Historical mail is being actively pruned out of the very accounts most likely to hold long archives.
  • Incremental sync depends on a proprietary extension. XYMHIGHESTMODSEQ is Yahoo-specific and undocumented publicly; anything built on it is unportable and unversioned, while the standard CONDSTORE alternative is simply absent (Probe Log).
  • inferred AI-crawler policy is enforced in infrastructure and will not be visible in robots.txt. Basis: mail.yahoo.com's 229-byte robots.txt names no AI agent, yet ClaudeBot, GPTBot, PerplexityBot and CCBot each received 429 Edge: Too Many Requests while curl, Googlebot, bingbot and a nonsense UA received 200 from the same IP in the same sweep (Probe Log). A crawler that only parses robots.txt will read this host as unrestricted and be wrong.
  • inferred Mail data sits outside Yahoo's OIDC self-service surface entirely. Basis: the login.yahoo.com discovery document advertises scopes_supported of only openid, openid2, profile, email (Probe Log), so the mail scope is not merely unapproved by default — it is not published to the standard OAuth discovery path that client libraries read.

Inferences

  • AI-crawler policy is enforced at the edge, not declared in robots.txt. Basis: four named AI UAs got 429 while four non-AI UAs got 200 from one IP in one sweep, against a robots.txt containing no AI rules (2026-09-01).
  • The mail scope is absent from Yahoo's published OAuth discovery. Basis: scopes_supported at login.yahoo.com/.well-known/openid-configuration lists only openid, openid2, profile, email (observed 2026-09-01).
  • Incremental IMAP sync is structurally more expensive here than on providers that ship CONDSTORE. Basis: the CAPABILITY response advertises XYMHIGHESTMODSEQ but neither CONDSTORE nor QRESYNC (observed 2026-09-01), so no standard MODSEQ-delta command is available.
  • Attachments deserve promotion to first-class documents. Basis: the 39.8 MiB APPENDLIMIT/SIZE ceiling admits full PDFs and Office files, and no server-side extracted-text field appears anywhere in the advertised capability set.
