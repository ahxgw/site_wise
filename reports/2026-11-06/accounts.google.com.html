Context

accounts.google.com is the sign-in and consent front end for every Google Account. Gmail, YouTube, Drive and other Google products redirect here to sign people in, and so does every third-party site that offers "Sign in with Google". Third-party sign-in has run on the Google Identity Services (GSI) SDK since its Aug 3 2021 launch. The host earns nothing directly. Its value is that it is the gate to Google's logged-in products and the identity layer under millions of other sites. For an index builder it is the clearest case of a zero-corpus host. Unlike mail.google.com, which disallows everything in robots.txt, this host allows everything, yet every path either redirects into a sign-in flow or returns machine-facing JSON. What can be indexed here is the identity protocol itself: discovery documents, signing keys, FedCM configuration, the OAuth scope catalog, and the error and consent semantics a crawler hits whenever it follows a Google sign-in link. Those error and consent pages are worth recognising, because they are the pages an index should exclude.

Retrieval Notes (site-specific deltas)

Only where this host differs from the default platform assumptions.

Allow-all without content

This breaks the usual crawl-policy model. The default assumption is that robots.txt marks the boundary between public and private. Here robots.txt opens the whole host, and the redirect into sign-in, plus the absence of indexable markup, does the closing. A crawler that treats Allow: / as a signal of public content will spend its budget on near-identical 0.8–0.9MB sign-in shells.

Link sink

Every Google sign-in link on the web (Gmail, Drive and Docs shares, YouTube actions, "Sign in with Google" buttons) resolves here. The URLs carry continue=, followup= and per-session dsh/as tokens, so URL dedup never collapses them. The useful signal is the continue target, which identifies the gated resource behind the link.

Identifier & dedup

sub is the stable Google Account ID (subject_types_supported: public), so it is the same for every relying party; email can change. Client IDs embed the Cloud project number as their numeric prefix, so one project's many client IDs group together. The error page does not map a client ID to an app name.

Freshness

The only objects here that change on a schedule are the signing keys. Fetch the JWKS no more often than its max-age allows; the overlap window between an old and a new key is what keeps cached keys valid. The FedCM config and the discovery document are effectively static, so a weekly diff is plenty.

Bot gating

The defences are browser checks, not UA or IP blocks. FedCM metadata answers BROWSER_NOT_SUPPORTED to scripts. The sign-in pages are served, but they are JavaScript-driven flows. Sending a crawler UA to test differential serving is not a legitimate probe on an authentication host, so this report did not do it.

Indexing Plan

  • Retrieval unit: none for content. Index this host as an entity, namely the Google identity provider, carrying its protocol documents as structured attributes: issuer, endpoints, algorithms, scopes, FedCM modes and current key IDs.
  • Page-class rule: classify any URL on accounts.google.com that is not JSON as an auth interstitial, drop it from the document index, and record the decoded continue= target as an edge to the gated resource. Count these edges per target host; that count is a usable signal of how much of another site sits behind Google sign-in.
  • Ingestion paths, ranked: 1) The well-known JSON (OIDC, FedCM, web-identity, assetlinks), fetched weekly. 2) JWKS on its max-age, with each new kid logged. 3) The scope reference plus API discovery documents, monthly, to keep a scope → API → sensitivity table. 4) Wayback for history. Crawling HTML yields nothing.
  • Derivatives: a scope-sensitivity map (scope → API → whether it is restricted), so that an index of any Google-backed app can say what data that app could reach; and a timeline of signing-key changes.
  • Demo to build: a "who sits behind Google sign-in" graph. Sample pages from a web crawl, extract GSI client IDs and accounts.google.com links, group client IDs by project-number prefix, and decode the continue= targets. It needs no authentication and shows the identity layer as a join key across sites.

Risks to the Index

  • Crawl-budget trap. Allow-all plus unique-per-session URLs plus pages near 1MB is the worst combination for a naive crawler. Without the page-class rule, every Google sign-in link on the web becomes a fetch.
  • Probing an IdP is sensitive. Credential-flow endpoints (/v3/signin/*, token endpoints) must never be exercised with guesses, and UA spoofing on an authentication host can look like evasion. Keep to the documented public JSON.
  • Verification gates bind reuse, not discovery. Any product built on Google account data runs into the 100-user cap and annual CASA reassessment (Verified Metrics). Plan for them before relying on Google-authenticated ingestion.
  • inferred The sign-in surface is moving into the browser. Basis: the FedCM config defines four modes and Google publishes web-identity at the registrable domain (Probe Log); once sign-in happens in a browser dialog, fewer accounts.google.com redirect URLs appear in links, which weakens the link-sink signal over time.
