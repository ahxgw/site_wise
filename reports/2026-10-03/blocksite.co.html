Context

BlockSite is a freemium site and app blocker for Chrome, Edge, Firefox, Android, iOS and desktop. Premium is a subscription; the homepage offered $33.50/year on 2026-10-03. The Chrome listing dates from September 2012. In July 2018 AdGuard tied it to "Big Star Labs", a Delaware company whose apps sent full browsing URLs to its servers (AdGuard). Today's publisher is BlockSite LP, at a Wilmington, Delaware registered-agent address. Its privacy policy says it may share "internet and electronic network activity information" with affiliates for market intelligence (privacy policy, modified 2026-07-16). This is not a content site. The two hosts in Site Wise's input are a Yoast-SEO WordPress marketing site (blocksite.co) and a React account dashboard (user.blocksite.co). The extension uses the dashboard as its block page. For an index builder the lessons are negative ones. The traffic rank measures blocking events, not demand for content. The dashboard answers every path with a 200 SPA shell. The public text corpus is about the size of one blog.

Retrieval Notes (site-specific deltas)

Only where blocksite.co differs from the default platform assumptions.

Traffic rank ≠ content demand

Top-site lists rank user.blocksite.co high because the extension redirects blocked navigations there (Probe Log: the CRX BLOCKED constant). Each attempt to open a blocked site counts as a dashboard pageview. So a large slice of the traffic is people being turned away. A crawl budget allocated by traffic would waste itself here. The same pattern should be expected for other extension-backed hosts, such as uninstall pages and new-tab replacements.

Soft-200 catch-all

user.blocksite.co answers every path, including robots.txt and sitemap.xml, with the same 200 HTML shell. A crawler that trusts status codes will record a "robots.txt" made of HTML and an infinite URL space. Detect it by the shell hash (two distinct shells, root and /app/) and by the noindex meta, then drop the host.

Query strings are the payload, and they leak

The block page carries its state in the URL (site=, blockType=, category=adult). The uninstall page carries analyticsUuid and the options page carries groupId. Those URLs end up in public archives: 2,259 URL keys in Wayback, rising from 29 in 2020 to 783 in 2026 so far. That makes them a crude "what do people block" signal. Each one is also a record of one person's browsing with a per-install ID attached. Exclude user.blocksite.co query strings from any URL-ingest pipeline that uses archives or referrer logs as seeds.

The marketing site is small and polite

The whole public corpus fits in two WP REST calls. Sitemap lastmod agrees with REST modified, so it can be trusted, unlike the sitewide-stamped dates on 2026-10-02's ThePornDude. The constraint is Wordfence: its per-IP lockout is far stricter than any CDN rate limit seen in recent reports. Pace at 1 request every 10s or slower; a full pass is about 125 requests, roughly 20 minutes.

Identifier & dedup

Use WP post id as the key; the category is in the path, so a recategorised post changes URL. Cross-store joins: Chrome ID eiimn…cgbh, Edge lbnbl…lnjgjk, the AMO GUID, Play co.blocksite and iOS 1474967653. All five resolve to one product entity. Expect version drift between stores: Firefox is stuck at 4.0.8.3 while Chromium builds are on 7.1.1.

Authoritative field

For claims about the product, store records beat the website. The site says "1,000,000+ users" and the CWS description says "over 5 million people". The only dated, measured figures are the per-store counts in Verified Metrics.

Indexing Plan

How Site Wise would build the index for this site.

  • Retrieval unit: a blog post (WP ID, title, body, category, featured image), plus a single product entity that joins the five store listings with version, permissions and ratings.
  • Primary keys & joins: WP post ID ↔ canonical URL ↔ featured_media ID. For the product: the store IDs above, keyed to the publisher "BlockSite LP". CRX hash_sha256 versions the code.
  • Ingestion paths, ranked: 1) WP REST /posts?per_page=100, 2 calls for the whole corpus; 2) one sitemap pass for pages and images (5 calls); 3) the keyless store APIs (Chrome ds:0, AMO, Edge, iTunes; 4 calls); 4) the Chrome update protocol for the CRX. Ceiling: about 125 objects plus one code package. Skip user.blocksite.co and category.blocksite.co entirely.
  • Recrawl cadence: REST weekly (diff on modified); store records daily for ratings and versions; CRX on hash change.
  • Derivatives to generate: text embeddings for the posts; a permission and endpoint inventory from the CRX (hosts contacted, obfuscated modules) as a "what does this extension phone home to" record. Skip OCR and ASR: there is no media worth it.
  • Demo to build: an extension-backed-host detector. Take top-site entries whose HTML is a noindex SPA shell answering 200 on random paths, and check whether a popular CRX names that host as a redirect target. That would flag traffic-inflated hosts like this one before crawl budget is spent on them.

Risks to the Index

Only risks that change indexing strategy.

  • Privacy contamination from seed lists. Archive- or referrer-derived seeds will contain block-page URLs that tie a per-install UUID or blocked host to a person's session. Filter user.blocksite.co query strings at ingest, not after.
  • Publisher trust. The 2018 AdGuard finding and today's policy language on sharing activity data with affiliates mean a "trusted productivity tool" label should not come from store badges ("Featured", "good record") alone. Keep provenance flags on the product entity.
  • Wordfence lockouts. An aggressive crawl gets the crawler's IP blocked for the whole apex. Budget for it, or ask support@blocksite.co for an allowlist.
  • Browser-policy shifts. The block page depends on <all_urls> plus webRequest/declarativeNetRequest redirection. Chrome policy changes or a store takedown (as in 2018) would remove the traffic but not the marketing corpus. Don't let traffic-weighted priors carry this host.
