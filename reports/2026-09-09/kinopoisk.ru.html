Context

Kinopoisk launched on 7 November 2003 as a hobby project by Vitaly Tatsiy and Dmitry Sukhanov — a Russian-language IMDb with a community grafted on. Yandex bought it in October 2013 and, from 2018, bolted a streaming service onto the reference database; the catalogue is now the discovery funnel for a Yandex Plus subscription. That two-layer structure is what makes it interesting to index: the reference layer is wide open and the video layer is entirely closed, with a single ID space joining them. Unlike every other Russian property in this series, Kinopoisk does not challenge crawlers — inferred it treats bot traffic as SEO supply rather than abuse. Basis: robots.txt carries zero AI-crawler directives, and Googlebot, ClaudeBot and GPTBot each received full 120KB server-rendered HTML from a US IP while a bare curl/8.7.1 agent was bounced to Yandex SSO (Probe Log).

Retrieval Notes (site-specific deltas)

Only where Kinopoisk differs from the default platform assumptions.

The structured data is the worst view

The usual assumption is that JSON-LD is the cheap, clean extraction target. Here it is the impoverished one: it omits budget, box office, admissions, premiere dates, crew beyond director/producer, the top-250 rank, and — on 23 of 25 sampled pages — the rating that is the site's whole reason for existing. All of it sits in the rendered HTML. Budget an HTML parser and use the JSON-LD only as a type discriminator.

A UA-conditional auth gate, not an anti-bot

inferred The SSO redirect is a login-continuity feature that incidentally filters unrecognised clients, not an abuse control. Basis: it is defeated by replaying a cookie the server itself sets on the redirecting response, it exempts every bot user agent tested including two AI crawlers, and there is no challenge to solve. The consequence inverts Ozon: identify honestly and you are served; identify as curl and you are not.

Identifier & dedup

The key is the numeric ID in /film/<id>/, /series/<id>/ or /name/<id>/ — no slug, so no slug drift. But film and series share one ID space and rating.kinopoisk.ru answers for both, so the path segment is a type hint, not part of the key. The 79 Clean-param tokens are the canonical strip list, and unlike Ozon's they are short, readable and stable (sort, perpage, ord, status, from).

Cross-modal joins

Unusually clean, and one is free money: rating.kinopoisk.ru returns an IMDb rating and vote count alongside the Kinopoisk one (11/25 sampled) — an implicit entity link to another catalogue, unauthenticated, one request per title, advertised by neither site. Internally, title ↔ person joins run through relative /name/<id>/ URLs in JSON-LD actor/director, capped at 10 actors in markup versus 58 credited in the HTML.

Freshness & recrawl

Sitemap lastmod is uniformly the previous day across all 7.42M entries, so the one signal most crawlers rely on carries zero information. Use instead /news.rss pubDate for editorial, num_vote from the ratings XML as a per-title change counter, and the review-page header counts for UGC. The ratings endpoint is replica-inconsistent, so require a threshold delta before triggering a recrawl.

Quality & spam

Reviews arrive pre-classified by the site into positive/negative/neutral with a computed positive percentage, and they are long-form prose rather than one-line ratings. Labelled sentiment at that length, in one language, across 79K titles is worth indexing for its own sake, independent of the film metadata.

Indexing Plan

  • Retrieval unit: one document per numeric title ID carrying the HTML-extracted field set — Russian and original titles, year, country, genres, full crew, budget/box office, premiere dates, age rating, runtime, top-250 rank, rating and vote count — plus the poster media ID. Person IDs are a second document class; reviews are children keyed by title ID + author handle + date.
  • Primary keys & joins: numeric title ID as root; /name/<id>/ for the credit graph; the IMDb rating pair from rating.kinopoisk.ru as the external reconciliation hint; avatars.mds.yandex.net media ID for imagery.
  • Ingestion paths, ranked: 1) Sitemap → rendered HTML fetch under an honest user agent — complete enumeration, no auth, no challenge, richest fields; the cost is 7.42M fetches and the ToS §5.2 question. 2) Ratings XML — ~150 bytes per ID, supplies the rating and the IMDb link, and backfills the 92% of titles whose JSON-LD lacks one. 3) /news.rss — the only true incremental feed, editorial only. 4) Image CDN by media ID — free, strictly downstream of 1. There is no fifth path: /api/* is disallowed and no public API is documented.
  • Recrawl cadence: people annually — 5.6M documents that barely move and dominate the corpus by count, not by value; title metadata quarterly; ratings weekly via the XML endpoint; reviews monthly where the header count moved; editorial hourly off RSS; images never.
  • Derivatives to generate: Russian-language embeddings over synopsis + review bodies — the review corpus is the differentiated asset. Skip thumbnailing and request the CDN's own size tokens. ASR is unjustified: no anonymous audio or video stream path exists.
  • Demo to build: an IMDb ↔ Kinopoisk reconciler driven purely by rating.kinopoisk.ru — pull both rating pairs for a sample of title IDs and score how reliably the (rating, vote-count) tuple identifies the same film in an IMDb dump. It tests whether the site's most overlooked endpoint is a usable cross-catalogue join key.

Risks to the Index

  • The open door is undocumented and therefore revocable. The absence of AI-crawler rules is an omission, not a grant, and the disable_server_sso_redirect bypass is an implementation detail one deploy away from vanishing. Record the ToS §5.2 conflict explicitly rather than infer permission from the 200s.
  • ToS §6.6 targets the rating specifically. Reusing the Kinopoisk Rating requires prior permission plus attribution — and that rating is the single field making this catalogue more valuable than a generic film database. Settle display rights before the number reaches a UI.
  • The reference layer exists to feed the subscription. If Yandex decides open metadata leaks discovery to competitors, the cheapest lever is moving title pages behind the same SSO gate that already fronts the player — the mechanism is deployed and tested.
  • Review indexing carries author identity. Reviews are signed with real display handles while /user/* profiles are crawler-blocked, so ingesting reviews reconstructs what robots.txt withholds. Handle retention needs a privacy decision up front.
  • Single-jurisdiction, single-operator infrastructure. One IP, Yandex nameservers, Yandex mail, Yandex CDN, a wholly Russian issuer — no third-party edge to fall back on and no non-Russian contracting route for a licensed feed.

Inferences

  • Kinopoisk treats crawler traffic as SEO supply, and its SSO redirect is a login-continuity mechanism rather than an anti-bot control — stated with their bases in Context and Retrieval Notes respectively.
  • The ratings endpoint reads from a lagging replica set. Basis: num_vote for the same title returned 1,098,451 then 1,098,247 minutes apart — a decrease a monotonic counter cannot produce from one source.
  • The sitemap is regenerated wholesale nightly rather than maintained per object. Basis: all 7.42M entries across 154 shards carry an identical lastmod, priority and changefreq.
  • Review pages run a materially older stack than title pages, so one parser will not cover both. Basis: inline self_url variables and URL-segment pagination on /reviews/ versus data-tid Next.js markup on /film/, plus the Windows-1251 encoding still emitted by rating.kinopoisk.ru.

Open Questions

  • Total review count across the catalogue — the sitemap names 79,014 titles that have reviews but not how many exist; needs a crawl of those review-index headers, which expose exact counts, and a sum.
  • Catalogue-wide rating coverage — 18/25 is too small to project onto 1.09M titles; needs a stratified sample of several thousand IDs against rating.kinopoisk.ru, cheap at ~150 bytes per response.
  • Size of the streaming catalogue as distinct from the reference database — no external probe separates "has a page" from "is watchable"; needs an authenticated Plus session or a Yandex disclosure.
  • Kinopoisk's own MAU, separate from the Plus bundle — Yandex reports subscribers, not per-service audience; needs a Mediascope panel figure or a Yandex Radar export.
  • Whether verified Googlebot/YandexBot receive anything the spoofed user agents did not — resolvable only from a reverse-DNS-verifiable crawler IP or via Yandex Webmaster access for the domain.
  • Whether the metadata surface differs from a Russian IP — every probe here came from one US address and none was geo-blocked, but showtimes and availability flags may vary; needs a paired run from a Russian egress.
  • Whether any partner or licensed metadata feed exists — no public API is documented and /api/* is crawler-blocked; needs a direct approach to Yandex industry relations.
