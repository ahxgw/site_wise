Daily Site Profile

drive.google.com

Google's file-storage host exposes no catalogue: public PDFs and folders surface only through outlinks, each page marked noindex, with owner metadata inline.

Cloud file storage User-generated files Google LLC noindex everywhere, no sitemap

Evidence: verified inferred (must state basis) open — conventions in the methodology.

Context

drive.google.com is the web front end of Google Drive, where users store and share arbitrary files. Logged out, the host is a login redirect. The only public surface is what owners expose through "anyone with the link" sharing: a file viewer at /file/d/{id}/view and folder listings at /drive/folders/{id}. Nobody announces those links. They spread through school sites, shops, forum posts, QR codes and apps that call the Drive SDK, and that is how they reach crawlers. For an index builder this is a large open store of PDFs and office files (catalogues, forms, circulars, filings) that Google itself marks noindex on every response. The page HTML carries file name, MIME type, byte size and an extension inline, so a link census gives typed metadata without downloading a byte. The actual bytes sit on drive.usercontent.google.com, whose robots.txt disallows everything.

Retrieval Notes (site-specific deltas)

Identifier & dedup

The fileId is the key. 96.8% of captures use a 33-character ID and 3.1% of distinct IDs are legacy 0B IDs. IDs are case-sensitive (one case-fold collision among 94,266 distinct IDs), so do not lowercase them. The same file appears under different usp= tags and with /view, /preview and /edit suffixes; strip all of them. 822 captures also carry a resourcekey. The 0B alias in the blob did not resolve as a URL (Probe Log row 7), so its role is open.

Retrieval unit

The file, keyed by ID, with name, MIME, size and extension from the page. The unit is useful only once bytes are extracted by an authorized path.

Cross-modal joins

Folder rows join to files by fileId and to parents by parent ID, both stable. The owner-email field is the only author key and is personal data. The file-page drive-viewer URL is an opaque token, not a stable key.

Authoritative content field

The itemJson name and MIME beat the HTML title (which appends " - Google Drive"). The file name is user-chosen and often a bare scan name such as 9487.pdf, so name alone is weak retrieval text.

Freshness & recrawl

Shared files rarely change. The recheck found 27 of 28 live after ten days, so recrawl is about link death, not content change. Recheck links on a slow cycle; a 401 means access was withdrawn, a 404 means deleted or never valid.

Quality & spam

No trust tier is exposed. Link spam via Drive shares is plausible but unmeasured.

Internal vs external search

Not applicable to anonymous users: there is no public search, and Google marks every page noindex, so even Google web search is told not to show them.

User query profile

Queries here are navigational, from someone who holds the link. Content queries ("2026 candle catalogue pdf") would target the file text, which only the owner-authorized path provides.

Indexing Plan

  • Retrieval unit: the file, with the folder as grouping context.
  • Primary keys & joins: fileId (33-character, case-sensitive) and folderId; parent ID joins files to folders. Treat legacy 0B IDs as a separate keyspace until the alias is understood.
  • Ingestion paths, ranked: 1) Common Crawl link census plus file-page and folder-blob metadata: no auth, ceiling roughly 94K files and 17K folders per crawl, no bytes. 2) Owner-authorized Drive API for the owner's own files: OAuth, 1M units per minute per project, full export. 3) Direct byte download: ruled out, drive.usercontent.google.com disallows all crawling and Google's terms bar ignoring robots.
  • Recrawl cadence: links monthly with the crawl cycle; folder listings about monthly; files only on change signals from an authorized API.
  • Derivatives to generate: none from public data alone, since no bytes are available. With owner authorization: text extraction and OCR for the PDF-heavy sample, thumbnails from the Drive-supplied render.
  • Demo to build: a link-graph census that reports, per outlinking site, how many Drive files and folders it exposes, with file name, MIME and size from the page blob and no downloads.

Risks to the Index

  • Blanket noindex plus robots disallow on the download host: an index built from this host contradicts Google's own signals and its terms. Any plan needs owner authorization or a policy decision.
  • Personal data: 25 of 27 sampled file pages expose an owner-email field. An index should drop or hash it before storage.
  • Wall hardening: the host already returns 401 for withdrawn shares, and Google can change the inline blobs at any time; the parsers rely on positional fields.
  • Link rot: 3.4% of file captures were 401 and 5.2% of folder captures were 404 at crawl time, and one of four sampled legacy-ID files had lapsed within ten days.
