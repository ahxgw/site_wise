Context

support.microsoft.com holds Microsoft's end-user help for Windows, Office/Microsoft 365, Surface, Teams and billing, plus the archived KB and hotfix corpus. It sells nothing: it is a cost-deflection surface whose job is keeping users out of paid support queues. That gives it an unusual posture for a top-150 host — it wants to be crawled, and its robots.txt blocks no AI crawler at all, a real deviation from the platform default. The welcome mat is thinner than it looks. The corpus ships as raw HTML with no JSON-LD, no feed and no content API, split across two URL namespaces that share nothing, behind an edge that 403s every user agent under load. inferred Microsoft optimises this host for search engines and human readers, not programmatic reuse. Basis: robots.txt names no AI crawler and lists two sitemaps, yet /api/ is disallowed, 0/10 sampled pages carry JSON-LD, no feed responds, and the Learn Catalog API excludes documentation (see Verified Metrics).

Retrieval Notes (site-specific deltas)

Only where this site differs from the default platform assumptions.

Two namespaces, one corpus

The defining structural fact: the collection sitemap publishes GUID-suffixed legacy URLs, _sitemaps publishes readable slugs, and the two en-us sets share zero URLs. inferred Only the slug namespace is canonical; the collection sitemap is a redirect index kept alive for inbound links. Basis: 99.9% of collection URLs are GUID-suffixed, 30/40 sampled 301 into slug targets with only 1 target retaining a GUID, and 10/10 slug pages are self-canonical (Probe Log). Ingesting both indexes naively duplicates most of the corpus.

Cross-locale join key

The site inverts the usual pattern — zero JSON-LD, but a ten-field meta block at 100% coverage — so extraction targets <meta>, not schema.org. Within it, awa-articleGuid is the article's identity across translations, identical in en-us, de-de, ja-jp and fr-fr for the same page, while document_id appears only on the en-us original (Probe Log). Join translations on awa-articleGuid; never key on the slug, which is localised.

Freshness is bimodal, and the sitemap lies about it

Half the en-us corpus carries a 2021 lastmod from a bulk migration. inferred Sitemap-index lastmod is a build stamp, not a content signal. Basis: all 640 collection children are stamped 2026-09-05T00:00:00Z while the URLs inside top out at a single 2026-07 entry (Probe Log). Recrawl from ms.date, not sitemap lastmod.

Crawl-friendly policy, hostile edge

The second delta from the platform default: robots.txt names no AI crawler, so there is no policy barrier — but the edge 403s every user agent under sustained load and recovers after roughly three minutes idle (Probe Log). The constraint is throughput, not permission: budget one patient crawler with exponential backoff, not a fleet.

Git-backed authoring, private repos

Every page names its source Markdown file and commit. inferred No bulk Markdown path exists despite that provenance. Basis: both MicrosoftDocs/enduser-*-pr repos named in the meta return GitHub API 404 while the public microsoft-365-docs control returns 200 (Probe Log). The commit hash remains useful as a change-detection key.

Absent from Microsoft's own AI index

The most surprising finding: microsoft_docs_search returned 0/30 results from this host across three queries squarely in its subject area, routing even "how to reset my Windows 11 password" to learn.microsoft.com/answers threads — yet microsoft_docs_fetch retrieves these pages as clean Markdown. Retrieval and fetch are decoupled: bring your own URLs.

Query profile

Two disjoint audiences share one host: consumer troubleshooting in natural language ("Outlook won't open") and IT-pro lookup by exact identifier ("KB5015901"). The /servicing/ subtree — the largest _sitemaps bucket at 163 children — serves the second and should have its KB number extracted as a first-class entity.

Indexing Plan

The actionable conclusion: how Site Wise would build the index for this site.

  • Retrieval unit: the H2 section of a locale-specific article, carrying the parent's product taxonomy. At a 485-word median, whole-article units are viable — but /servicing/ KB pages run past 20K characters and must be split.
  • Primary keys & joins: awa-articleGuid as the cross-locale article identity; document_id as the en-us source pointer; canonical slug URL as the display key; git_commit_id as the change-detection key; KB number parsed from /servicing/ titles as the entity join to Windows update data.
  • Ingestion paths, ranked: 1) _sitemaps/sitemapindex.xml for the canonical slug URL set — no auth, 34,449 en-us URLs, the only namespace worth enumerating. 2) microsoft_docs_fetch for clean Markdown per URL — no auth, quota undocumented, measure before depending on it. 3) Direct HTML crawl with <meta> extraction as fallback, and the only route to embedded media — throttled to 403 under load. 4) collection.xml only as a redirect table for inbound legacy links, never as a content source.
  • Recrawl cadence: /servicing/ update KBs weekly, tightening around Patch Tuesday; articles with a ms.date inside 12 months monthly; the 2021-stamped back catalogue quarterly, since 54.6% of it has not moved in five years. Trigger on git_commit_id change, not sitemap lastmod.
  • Derivatives to generate: OCR on embedded UI screenshots, which carry menu paths and dialog labels the prose omits and users type verbatim into search. Embeddings on en-us text only, joined to translations via awa-articleGuid — re-embedding 40 near-identical locales buys little. Skip ASR; there is no meaningful audio corpus.
  • Demo to build: a legacy-URL resolver — resolve the 49,664 en-us GUID URLs to their canonical slugs and publish the mapping. It turns the site's biggest dedup hazard into a lookup table and measures what share of the old KB corpus is dead rather than merely moved; the 40-URL sample already found one redirecting to the bare homepage.

Risks to the Index

  • Consolidation into learn.microsoft.com. answers.microsoft.com was absorbed wholesale (Probe Log) and Microsoft Docs was folded into Learn in 2022. Support content is the remaining outlier, and its absence from the Learn search index reads as unfinished migration rather than deliberate exclusion. A move would invalidate every URL key at once; awa-articleGuid is the only key likely to survive.
  • MCP fetch is an undocumented dependency. The cleanest text path is a tool whose published purpose is Learn documentation — no stated quota, no support commitment for this host, no guarantee it keeps resolving these URLs. Never make it the only ingestion path.
  • Republication is restricted. Microsoft's permissions policy allows linking but not independent republication, and notes Microsoft does not own every article and image on its pages. Snippets and links are safe; mirroring article bodies is not.
  • Edge throttling caps throughput invisibly. The 403 is indistinguishable from a genuine block unless you test recovery — a naive crawler records half the corpus as forbidden, and any coverage metric computed during a throttled run is wrong.
  • KB deprecation churn. Articles for end-of-life products retire to landing pages rather than 404s, so a redirect chain that still returns 200 can silently mean the content is gone.

  • Does microsoft_docs_fetch have a rate limit or terms-of-use position on bulk retrieval of support.microsoft.com URLs? Ask Learn Integrations Support, or measure the throttle against the endpoint.
  • What is the per-IP request budget before the edge 403s, and the exact recovery window? Ramp concurrency stepwise against a fixed control URL, recording first failure and time to first success.
  • How many images and videos does the corpus hold? Raw HTML shows one <img> on most pages, but body media loads client-side — a headless render of a stratified sample would give a real count.
