Context

Gmail is Google's email client, launched April 1 2004 and now serving 3B users. It is free for consumers (monetized through Google One storage upsell and Workspace seats) and paid for the 10M+ businesses on Workspace. For an index builder it is the cleanest example on the top-100 list of a zero-crawl host: enormous traffic, essentially no public corpus. The retrievable object is the RFC 2822 message inside one person's mailbox, and the only legitimate path to it is that person's OAuth grant. That inverts the usual economics — the meter is not rate limit but compliance: Gmail's scopes are all restricted, which means an annual third-party security assessment before you may touch a single mailbox at scale. inferred Google treats the hostname itself as the permission boundary. Basis: the Gmail API discovery document lists https://mail.google.com/ as one of its 14 OAuth scopes — the full-mailbox scope is literally spelled as the site's URL (probed 2026-07-27).

Retrieval Notes (site-specific deltas)

Only where Gmail differs from the default platform assumptions.

Identifier & dedup

Two ID systems that must not be confused. Gmail's id and threadId are mailbox-local — the same email in sender's and recipient's accounts carries different IDs. The globally stable key is the RFC 2822 Message-ID header, searchable via q=rfc822msgid:. Cross-mailbox dedup is only possible on Message-ID; anything keyed on Gmail's id silently double-counts.

Retrieval unit

The thread, not the message. Gmail's product model is conversational and users recall threads ("the invoice chain with the landlord"), but attachments and markup hang off individual messages — so index the thread as the retrievable card with per-message parts as sub-records.

Cross-modal joins

attachmentId joins media to message; historyId is a per-mailbox monotone sequence that joins every mutation into one changelog. The discovery doc warns it is non-contiguous with random gaps — treat it as a cursor, never as a count or a delta size.

Authoritative content field

internalDate beats the Date: header: the API documents it as the time Google accepted the message, and it is what orders the inbox. The Date: header is sender-supplied and routinely wrong or forged. For time-ranked retrieval, internalDate is the only trustworthy clock.

Freshness & recrawl

Never re-poll. users.watch pushes to Cloud Pub/Sub, and history.list costs 2 units — a tenth of one messages.get. Incremental sync from a stored historyId is so much cheaper than enumeration that full re-listing is a bug, not a fallback.

Quality & spam

Roughly 10M spam messages a minute are stopped before delivery (Verified Metrics), so the mailbox arrives pre-filtered — but messages.list takes includeSpamTrash, and setting it silently changes the corpus. Also note phishing is adversarial content inside the index; a mailbox index will happily retrieve a convincing fake invoice.

Internal vs external search

There is no external option. Gmail search operators are the whole query language, and the API exposes them verbatim through q — so an index builder can push predicates server-side rather than pulling and filtering. The catch: the cheap gmail.metadata scope explicitly forbids q, forcing the expensive scope on anyone who wants search pushdown.

User query profile

Re-finding, not discovery. Queries are person-anchored and artifact-anchored ("the flight confirmation from March", "what did Priya send about the contract") over a corpus the user already saw once. Recency and sender identity outrank topical relevance.

Indexing Plan

  • Retrieval unit: thread, with per-message MIME parts, attachments, and extracted schema.org entities as sub-records.
  • Primary keys & joins: partition key is always (userId, threadId) — never a bare message ID. Cross-mailbox identity on Message-ID; mutation cursor on historyId; time on internalDate.
  • Ingestion paths, ranked: 1) Gmail API — the only real path; one-time backfill via messages.list + get (≈5.6 h per 100K-message mailbox), then users.watch → Pub/Sub → history.list forever. 2) Takeout MBOX — user-initiated, no OAuth verification burden, preserves labels via X-Gmail-Labels; good for import-once products, useless for freshness (7-day expiry, no delta). 3) IMAP — works without restricted-scope review but caps at 15 clients per account and gives no label or thread model. 4) Crawl — yields three marketing pages and nothing else.
  • Recrawl cadence: push-driven only. Bodies and attachments are immutable, so re-fetch nothing; replay history.list for label, read-state, and delete events. Re-enumerate solely to repair a lost cursor.
  • Derivatives to generate: attachment OCR, thread summarization, sender-entity resolution, and schema.org entity extraction into a personal timeline. All must be computed and stored per-user — the Limited Use policy makes a pooled cross-user embedding store non-compliant, which also forecloses the usual cost-amortization play.
  • Demo to build: a quota-aware mailbox indexer that runs the arithmetic before it runs the sync — given messagesTotal from getProfile, project backfill wall-clock at 300 msg/min, then show the same mailbox staying current on history.list deltas for ~2 units a poll. The point of the demo is the ratio, not the retrieval.

Risks to the Index

  • Compliance is the real quota. Every Gmail scope is restricted, requiring OAuth app verification, a demo video of the full grant flow, and an annual security assessment by a Google-empanelled assessor if you store or transmit the data. This is a recurring yearly gate on continued access, not a launch cost.
  • The Limited Use policy blocks the standard index architecture. Data may only power features "prominent in the requesting app's user interface," and model training on it requires explicit user consent. A shared cross-user index — the thing that makes search economics work — is out of bounds by construction.
  • Quota was rewritten this year and gains a price tag. The limits changed May 1 2026 and the docs state overages are planned to bill to Cloud accounts later in 2026. A free-tier assumption baked into a sync scheduler will start costing money mid-year.
  • Project-level concurrency binds before user-level does. At 200 concurrently syncing users per project (Verified Metrics), scale is a matter of provisioning Cloud projects, not of optimizing calls — a constraint that has to be designed in early.
  • inferred Google is building the first-party version of exactly this index. Basis: the Jan 8 2026 blog post announces Gemini-powered retrieval inside Gmail, and Workspace's privacy hub confirms in-domain processing is permitted while third parties face restricted-scope review — an asymmetry that widens as the feature set grows.
