Context

Discord is a real-time chat platform organised into user-run servers ("guilds") of text, voice, video and forum channels. It launched in May 2015 as a gaming voice tool and became general-purpose community infrastructure. It remains private, monetising through Nitro subscriptions, server boosts, in-app commerce, and an advertising business built out across 2025–2026 (Quests, Orbs, mobile ad formats).

For an index builder Discord is the sharpest example of a corpus that is enormous, current, and almost entirely out of reach. Conversation lives at /channels/…, which robots.txt disallows and which requires an authenticated session regardless. What is crawlable is a directory shell: listing pages for servers that opted into Discovery, plus an app directory — a catalogue of communities, not of what they say. The one exception is small and precise: 265 announcement posts from 8 partner-scale servers are published as full public pages with message text in JSON-LD (Probe 9). The interesting asymmetry is that Discord's robots.txt carries no AI-crawler directives at all — it does not need them, because architecture already does the work robots.txt does elsewhere.

Retrieval Notes (site-specific deltas)

Only where Discord departs from the default platform assumptions.

No AI-crawler stance to read

The default assumption is that robots.txt blocks AI crawlers and the report notes deltas. Discord has no such lines at all (Probe 1), and its docs host affirmatively grants training rights (Probe 10). Read this as architecture substituting for policy: the valuable corpus was never on a crawlable URL, so there is nothing for robots.txt to defend. The binding constraint is the Developer Policy, not the crawl file.

The two-track split collapses

Methodology expects a curated SEO sliver plus a metered API. Discord has the sliver — 51.1K pages — but the API track does not lead to content: a bot only sees guilds that installed it, so there is no coverage ceiling to raise by paying. No credential tier turns Discord into a crawlable corpus.

Identifier & dedup

Snowflake IDs are the real key and embed a creation timestamp. Directory URLs are slug-{snowflake}, and the slug is derived from a mutable server name — index on the trailing snowflake and treat the slug as a label. Apps are deliberately dual-published at two paths (Probe 3); canonicalise to /application-directory/{id} or you double-count 18,392 objects.

Retrieval unit & authoritative field

The community, not the page or the message: a Discord result answers "which server should I join for X". Across the 32K directory the self-written description is the only topical text and it is promotional, so ranking should lean on the measured fields — member count, presence ratio, the 168-bin histogram — which are far harder to fake. Announcement pages invert this: articleBody is genuine prose, so index those 265 at full text and the directory as metadata.

Freshness, staleness & spam

Two clocks: listing text is near-static, while counts and activity are live per request (Probe 6). Sitemaps carry no lastmod and already contain dead URLs within a day (Probe 4), so treat one as a candidate set to verify, not a change feed. The ~1,000-member Discovery floor pre-filters the directory, so listing spam is milder than an open UGC index; the real failure mode is servers that cleared the bar once and have since emptied, which the presence-to-member ratio detects.

Internal vs external search

In-app search covers only servers the user has joined, so cross-server discovery has no native answer and users leave for external search and third-party server lists. That gap is the actual retrieval opportunity here — and it is the reason the directory is SEO-indexable at all.

Indexing Plan

  • Retrieval unit: the guild, keyed by snowflake. One record per server carrying description, category breadcrumb, member and presence counts, boost tier, feature flags, activity histogram, and icon/banner hashes. A second, smaller unit for apps.
  • Primary keys & joins: guild snowflake joins the directory page, the invite API record, and CDN asset paths built from the icon/banner/splash hashes. Application snowflake joins the two app URL forms. The vanity URL code is a soft alias — transferable, so never a primary key.
  • Ingestion paths, ranked: 1) servers sitemap → 32,252 pages, no auth, gives text plus JSON-LD, ceiling is Discovery-eligible servers only; 2) invite API on vanity codes harvested from those pages, no auth, adds live counts and the activity histogram, ceiling is 50 req/s and only servers with a resolvable code; 3) app-directory sitemap → 18,392 apps, no auth; 4) announcements sitemap → 265 posts with full message text, no auth, ceiling is 8 participating servers; 5) docs llms.txt, trending-games and blog RSS for first-party text. There is no sixth path — general message content has no legitimate bulk route at any price.
  • Recrawl cadence: directory text monthly; member and presence counts weekly for the head, monthly for the tail; sitemap diffed nightly to catch additions and 404s. Docs on release; blog RSS every few days, since the feed holds only 10 items.
  • Derivatives to generate: category and topic labels from description text; an activity score from the 168-bin histogram (peak, mean, and dead-hours count); a liveness flag from presence ÷ members; embeddings over name plus description for semantic community search. Skip OCR and ASR entirely — there is no qualifying media.
  • Demo to build: "find me an active server about X" over the full 32K directory, ranked by embedding similarity and then re-ranked by the measured activity score — the one claim worth demonstrating is that the histogram beats the self-description at predicting whether a community is actually alive.

Risks to the Index

  • The invite API is the fragile leg. It is the only unauthenticated source of live counts and the histogram, and liveliness is undocumented on an endpoint whose robots allowance could narrow without notice. Anything downstream should degrade to listing-page JSON-LD.
  • Age verification hardens the shell. Rollout slipped to H2 2026; if verification reaches directory or invite resolution for age-restricted communities, part of the crawlable surface moves behind a login.
  • Policy, not robots.txt, is the enforceable limit. "You may not mine or scrape any data, content, or information available on or through Discord services" is broad enough to cover directory crawling even where robots.txt allows it, and the authoritative text sits behind a 403 (Probe 11). Any programme here needs a written read from counsel, not a robots parser.
  • An IPO would change disclosure, not access. A public S-1 would settle revenue and server counts without opening the corpus; public-company scrutiny of data handling tends to tighten third-party access.
  • Discovery eligibility is a moving floor. The indexable set is defined by a threshold Discord sets unilaterally; raising it shrinks the corpus overnight with no signal but sitemap shrinkage. Alert on it.

Inferences

  • Discovery listing requires roughly 1,000 members. Basis: Probe 5 — across 25 pages sampled at fixed stride, the minimum was 1,230 and none fell below 1,000, which is what a hard floor looks like in a stratified sample. Discord's eligibility article is 403-blocked (Probe 11), so the exact rule is unconfirmed.
  • The crawlable directory is a small fraction of all servers. Basis: 32,252 listed (Probe 3) against 90M+ daily active users. Even at hundreds of members per community the listed set is a sliver.
  • The marketing site is served from Webflow, separately from the app. Basis: Probe 2 — surrogate-key: prod-wf1.discord.com plus preconnect/preload hints at cdn.prod.website-files.com.
  • liveliness.msg_activity_bins is a one-week hourly activity histogram. Basis: Probe 6 — exactly 168 integers (7×24) beside a last_updated_ts, under a field named msg_activity. The unit is undocumented.
  • CDN asset hashes act as version keys. Basis: Probe 7 — a 31-day max-age on a hashed path means a changed icon must mint a new hash, since the old URL stays cached.

Open Questions

  • How many servers exist, and how many are active? No official figure is published; EDGAR returns nothing (Probe 12). A public S-1 or a company post would close it.
  • What is Discord's revenue? Third-party estimates conflict (Sacra put ARR near $725M entering 2025; aggregators cite lower figures) and none is auditable. Only a public S-1 closes this.
  • What unit are the msg_activity_bins integers — raw message counts or a normalised 0–100 index? The observed series peaks at exactly 100 once, hinting at normalisation without establishing it. Sampling guilds of very different sizes would distinguish the two.
  • Is the servers sitemap complete or a capped sample? Compare its count against paginated /servers category totals over several days.
  • What are the Discovery eligibility rules in Discord's own words? The support articles 403 automated clients (Probe 11); a browser session or archived snapshot would settle it.
  • Does any licensing path exist for message content — research programme or partner access? Nothing appears in the developer docs; a direct inquiry to developer relations would answer it.
  • Why do only 8 servers publish public announcements, and is the surface growing? The set is small enough to look like a partner pilot. Diffing the announcements sitemap weekly is the best leading indicator that Discord will expose message content to the open web.
  • Are announcement pages a durable archive or a rolling window? With only 265 posts it is unclear whether old ones are removed. Re-fetching today's URL set in 90 days would settle it.
