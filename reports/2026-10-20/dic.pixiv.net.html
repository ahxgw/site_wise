Context

ピクシブ百科事典 (pixiv Encyclopedia, "pixpedia") is a user-edited wiki that pixiv launched in November 2009 to explain the tags and user projects on its illustration platform. Each article is a pixiv tag: the URL path is the tag string, and the page embeds artworks carrying that tag. Coverage is otaku culture, including characters, series, VTubers, doujin circles, memes and fandom slang. Mainstream encyclopedias cover little of this, often nothing at all. Revenue is display advertising; pixiv's large ads.txt is served on this host too. For an index builder it is the entity layer for Japanese fan culture. Each article gives a reading (yomigana), a category, a parent/child/sibling hierarchy, an English name for some entries, and a direct join to pixiv's work corpus of 177M+ items. The catch: the live host challenges every non-browser request, so legitimate access runs through archives and pixiv's own tag API.

Retrieval Notes (site-specific deltas)

Only where pixiv百科事典 differs from the default platform assumptions.

The tag is the primary key

Article URL, pixiv search tag and API key are the same string. That gives a free join from encyclopedia entity to every pixiv illustration, manga and novel carrying the tag. Normalize carefully: the ja and en editions use different strings (初音ミク vs Hatsune Miku, linked only through hreflang/translatedTagName), and en URLs mix %20 and +. The numeric id is stable but sparse, so use it as a secondary key, not for enumeration.

Sitemap parts are a creation log

inferred Parts are filled in article-creation order and appended at 1,000 URLs each. Basis: part 1 holds 2009–2010 articles, and part 693's earliest lastmod is 2026-04-27; the max part number rises monotonically in every monthly CDX snapshot. Fetching only the newest one or two parts therefore captures new articles, while lastmod across all parts drives re-edits.

The closed front door, the open side door

Unlike the default two-track picture, there is no public track at all on the host itself: even sitemaps and the OGP image endpoint are challenged. pixiv's tag API on www.pixiv.net stays open, and robots does not disallow it. It returns the curated abstract and the hierarchy, which is the highest-value slice for an entity index. Full article bodies are reachable only through archives.

Body is an AST, not HTML

get_article.nodes is a typed tree of text, headings, links, tag links, illust and video embeds. Chunk on its toc headings rather than scraping rendered HTML. Tag links in the body give an article-to-article link graph without any DOM parsing. JSON-LD carries only headline, dates and one image.

Language and reading

Nearly every article carries a hiragana yomigana, which is valuable for Japanese query normalization (kana input, voice) and rare on other sites. English coverage is thin (22.2K en URLs; 2 of 10 sampled ja articles had an English name), but the tag API's tagTranslation adds ko/zh/th/ms/romaji labels for multilingual alias tables.

Crawl policy

Unusually for a wiki, Googlebot is kept off edit and history paths, but /ac/ is left open to it while Bing is barred. The 12-UA training block also names omgili, Diffbot and cohere-ai. AI search/user agents (OAI-SearchBot, Claude-User, PerplexityBot) are not named, but the Cloudflare challenge makes that moot.

Indexing Plan

  • Retrieval unit: article keyed by tag string, with sections chunked on toc. Entity card = abstract + yomigana + categories + parent/children + main illust ID.
  • Primary keys & joins: tag string (→ pixiv works by tag); numeric article id; ja↔en via hreflang; illust IDs → pixiv.net/artworks/{id}; YouTube/niconico IDs from embeds.
  • Ingestion paths, ranked:
    1. Tag list from the archived sitemap (715K tags), then the pixiv tag API for abstracts and the hierarchy. At 1 req/s that is ~8.3 days for the full set (calculated by Site Wise).
    2. Wayback id_ captures for full __NEXT_DATA__ bodies, prioritized by views and works counts. Wayback throttles hard, so pace at ≤10 req/min; coverage is open.
    3. A licensed feed or allowlisting from pixiv for the live host, the only path to complete, current bodies.
  • Recrawl cadence: tag API monthly for the full set; weekly for tags whose sitemap lastmod moved (once a fresh sitemap is obtainable) and for the newest parts.
  • Derivatives to generate: a Japanese fandom alias table (tag ↔ yomigana ↔ en/zh/ko), a character→series→franchise hierarchy, and an article link graph from AST tag links.
  • Demo to build: a fandom entity resolver. Given a character name in kana, romaji or English, return the pixpedia card, parent franchise and top pixiv works via the tag join, using the tag API only.

Risks to the Index

  • No current bulk path: the live sitemap has not been archived since 2026-05-01, and every non-browser fetch is challenged. Article counts and bodies age unless pixiv grants access.
  • Side-door fragility: the tag API is an internal web-app endpoint (anonymous session cookie, undocumented). pixiv can gate it the same way, so cache abstracts aggressively.
  • Training use is opted out for 12 named crawlers on both pixiv hosts; keep any use in a search/retrieval role.
  • Adult and sensitive content: many articles describe R-18 tags (one sampled title was explicit) while isSensitive was false on all 10 sampled pages. Filter on categories and pixiv's work flags, not the article flag alone.
  • Image rights: article images are third-party pixiv artworks; display thumbnails linked to pixiv only.
