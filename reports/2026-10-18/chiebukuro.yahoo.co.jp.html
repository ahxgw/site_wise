Context

Yahoo!知恵袋 (Chiebukuro, "bag of wisdom") is Yahoo! JAPAN's community Q&A service: a user asks, others answer, and the asker may pick a ベストアンサー (best answer). It launched in April 2004 and is now run by LY Corporation, the 2023 merger of Yahoo Japan and LINE. Revenue is display advertising (the YDN yads tag loads on every sampled page). For an index builder it is the largest Japanese-language corpus of question → answer pairs, covering health, law, money, relationships and consumer problems back to 2004. It is also easy to enumerate: one sitemap file per day of closings since launch, schema.org QAPage markup on every thread, and the same bytes for every user agent. LY now feeds this corpus to its own RAG answer product, "みんなの知恵袋", which cites up to five past best answers per reply. That makes the archive both a retrieval asset and something LY has a reason to protect.

Retrieval Notes (site-specific deltas)

Only where Chiebukuro differs from the default platform assumptions.

The sitemap is a closings log, not a URL list

Each daily file lists the threads that closed that day (Probe Log). Open questions are kept out of both the sitemap and the index (noindex). The file set is append-only and needs no lastmod: to stay current, fetch yesterday's file (~1.8MB) each day. Deleted threads should drop out of their old files, so re-HEADing the full set and diffing Content-Length gives a deletion signal per day of history without downloading 14.9GB (first baseline: this census).

Identifier & dedup

One URL per question; IDs never change and threads self-canonicalize. Strip ?fr= (it appears even in og:url) and ?sort=. Because the shard prefix is s mod 5, the ID space can be walked without the sitemap: every 5th sequence number in each shard, about 24.8K/day (Verified Metrics). The sitemap is the better route, since 20% of IDs are gone and some live threads are still open.

Retrieval unit

The useful unit is the (question, best answer) pair, plus the other answers ranked by upvoteCount. LY's own RAG product retrieves on exactly this pair (Verified Metrics). Titles are the first ~50 characters of the question body, so og:title adds nothing; embed the full question text. Answers are long-form Japanese, often with URLs to official sources, so outbound-link extraction is a cheap citation layer.

Sitemap coverage gap

inferred A share of closed, indexable threads never reaches the sitemap. Basis: 6 of 64 live random IDs were closed and index but absent from every July–October file. LY's 160M best-answer count (2024) also exceeds the 139.9M sitemap total, and each thread has at most one best answer. A full corpus therefore needs the ID walk as a supplement, not only the sitemap.

Volume is falling fast

Daily closings dropped from ~30K (2022–2024) to 16.4K (autumn 2026). The 2020–2022 peak sits in the pandemic years. For a retrieval index this changes the mix: the back catalog (2009–2013 and 2020–2024) dominates, and answers about prices, laws and apps go stale. Rank by recency for time-sensitive categories, and add a staleness flag from datePublished.

Crawl policy

The policy is name-based and the server does not enforce it (UA matrix). The unusual detail is the Google-Extended split: Google may use thread pages for Gemini training (detail. allows it) but not the top/category host. OpenAI, Anthropic, Meta, Apple and Common Crawl training crawlers are blocked on both hosts. AI search/user agents (OAI-SearchBot, Claude-User, PerplexityBot) are not named, so they fall under *.

Indexing Plan

  • Retrieval unit: thread keyed by question ID; child records = answers (best answer flagged, upvoteCount, date); category path from breadcrumbs.
  • Primary keys & joins: question ID (numeric sequence s is the sort key and an approximate timestamp); category ID; question-image key que-{qid}. Author names are masked and not a stable join key.
  • Ingestion paths, ranked:
    1. Daily sitemap file → fetch ~16K threads/day, about 6GB of HTML/day at ~380KB/page (calculated by Site Wise). Extract JSON-LD only and discard the rest.
    2. Backfill: 8,223 historical files → 139.9M threads, about 53TB of HTML at full page weight (calculated by Site Wise). At 1 req/s that is 4.4 years, so backfill needs either agreed higher concurrency or a data deal with LY.
    3. ID walk over the sequence to catch the sitemap gap (~9% of live closed threads in the sample), at polite rates and only on ranges already closed.
  • Recrawl cadence: new threads daily from the latest file; closed threads only for deletion checks, through a monthly HEAD sweep of all children (8,223 HEADs) and refetching IDs from files whose size dropped.
  • Derivatives to generate: Japanese embeddings for question and best answer; an outbound-URL citation graph; a staleness score per category; OCR on the rare question images (mostly screenshots).
  • Demo to build: a "みんなの知恵袋" replica. Ingest one month of closed threads (~500K), retrieve the top-5 best answers for a new Japanese question, and compare the citations with LY's own AI answer for the same question.

Risks to the Index

  • Geo-wall: Yahoo! JAPAN services have refused connections from the EEA and the UK since 2022-04-06 (Yahoo! JAPAN notice). Crawl infrastructure must sit outside those regions.
  • LY monetizes the same corpus: its RAG product uses the best-answer archive. The open sitemap and unenforced robots could be tightened the way other platforms closed their public crawl. Snapshot the full sitemap set now; it is 14.9GB of XML.
  • Training use is opted out for every major lab except Google on the thread host. An index feeding model training must stay in a search/retrieval role.
  • Deletion churn: 20% of recent IDs already 404. An index must honour removals by running the deletion sweep, especially for personal advice threads.
  • noarchive: LY asks for no cached copies. A display index should show a snippet and link, not the full thread.
